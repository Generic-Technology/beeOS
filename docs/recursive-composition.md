# 递归组合：复合组件怎么嵌套、怎么跑

> **这份稿子讲「怎么跑」**。
> 模型与不变式在 [component-plugin-model.md](component-plugin-model.md)
> （那是「组件与插件」的总稿）；这份只讲**递归**这一件事的
> 声明形状、递归装配规则、子链执行、插件挂任意节点。
>
> **两份各管一段，不重叠**：总稿说「组件能嵌套」，这份说「嵌套之后怎么跑」。

## 0. 为什么要单独一份

递归组合要改的东西**跨三层**（core 的声明与装配、runtime 的执行、插件的宿主），
而总稿的主轴是**插件协议**。把递归的细则塞进去，
那份稿子会从「组件与插件」变成「组件、插件与递归」——**名字就不准了**。

| 稿子 | 管什么 |
| --- | --- |
| [component-plugin-model.md](component-plugin-model.md) | **是什么**：概念、不变式、插件契约、批次表 |

## 1. 目标形态

总稿 §1.1.2 的目标模型：

```text
BeeBox
└── 复合组件 A
    ├── 作业组件 B
    └── 复合组件 C
        └── 作业组件 D
```

**「复合组件」今天是盒子**（整盒就是一个复合组件）。
M8 要做的是：**盒子里也能有复合组件**，于是盒子不再是唯一的复合组件。

---

## 2. 本批做哪几件、不做哪几件

### 2.1 做

1. **盒内可以声明嵌套的复合组件**（复合里装复合）
2. **插件可以挂在任意节点**：作业组件 / 复合组件 / 盒子
3. **装配期递归校验**：入口、孤岛、环、形状、产出，全部按「作用域」递归判

### 2.2 不做（并说清为什么现在不做）

| 不做 | 为什么 |
| --- | --- |
| **跨盒引用 / 复用复合组件** | 要引入「复合组件注册表」+ 引用语义 + 版本。本仓**一条作业路线 = 一只盒子**（beeline 与盒子 1:1），现在没有任何「同一个复合组件被两只盒子共用」的真需求 → **先不造**。等真出现（跨盒共用的抽帧层、共用的校验腿），再按注册表那一套来 |
| **复合内部的分叉与汇聚** | 分叉时「后面的跳吃谁的数据」没有答案 → 需要**统一上下文**（谁建、装什么、子组件怎么读）。本批的复合内部**是一条链** |
| **输出映射**（父组件转换 / 筛选子组件的结果） | 本批用总稿 §3.1 的「父 ⊆ 子」这条更严的规则（见 §5.4）→ 不需要映射 |

**「不做」不是「以后再说」**：每一条都带着**触发条件**——
真出现那个需求的那一批，才把对应的机制带进来。

## 3. 声明形状：两个类，不是一个

### 3.1 为什么不是「`Component` 加一个 `children` 字段」

`Component` 现在专指**作业组件**（一跳），而**这个标识符不能烧**——
仓里的退休机制判在 AST 类名上：烧掉 `Component`，
将来通用组件类就再也叫不了 `Component`（总稿 §1.5 说清了这个代价）。

所以：

- **`Component`（作业组件）不动**
- 新增**第二个类 `CompositeComponent`**（复合组件）

总稿 §1.5 的「通用组件落成代码里的类」那一批**不由 M8 触发**——
M8 只多了一个具体类型，通用概念仍在文档层。

### 3.2 `CompositeComponent` 的字段

| 字段 | 是什么 | 跟作业组件一样吗 |
| --- | --- | --- |
| `op_id` | 盒内唯一（**全树唯一**，见 §4.6） | 一样 |
| `type` | 执行时的分派键 / bee 标签 | 一样 |
| `input_from` | 数据来源：`external` = **本作用域的输入**；否则是同层的某个 op | 一样 |
| `input` / `output` | 吃 / 吐的形状（schema id） | 一样 |
| `next` | 执行完接着跑哪几跳（**同层**） | 一样 |
| `children` | **子组件**（`Component \| CompositeComponent`，**至少一个**） | **复合组件独有** |
| `plugins` / `requires_plugins` | 横切能力 | 一样 |
| `idempotency` | 幂等档 | 一样（但**取值由子节点推导**，见 §4.5） |
| `leaves_artifact` | 成功后会留下东西吗 | 一样（但**取值由子节点推导**） |
| `timeout_seconds` | 这一节点的总预算 | 一样（但**受子节点约束**，见 §4.5） |
| `handler` | —— | **没有**（复合组件不直接执行） |

### 3.3 「既有实现又有子组件」——**写不出来**

复合组件**没有 `handler` 字段** → 这种自相矛盾的声明**在模型层就不存在**
（总稿 I15「插件不改形状」是同一条纪律的另一个面：
**别的东西也别想在模型层写出矛盾**）。

而作业组件**没有 `children` 字段** → 「作业组件里塞子组件」同样写不出来。

**两个角色的判据是结构性的，不是校验出来的** ✓。

### 3.4 盒子声明里怎么放

`assemble(declaration, components, ...)` 的 `components` 参数类型放宽成：

```text
list[Component | CompositeComponent]
```

`CompositeComponent.children` 同样宽（可再嵌套）。

**为什么是一个列表而不是两个**：**链是一条事实**。
分两个列表就要在两处维护顺序与边 → **两份事实**，
而两份事实迟早给出不同答案（总稿那条纪律）。

## 4. 装配期：把 C1–C12 改成「按作用域递归跑」

### 4.1 作用域（scope）：盒是**最外层**的作用域

| 作用域 | 输入 | 产出 |
| --- | --- | --- |
| **盒** | 投料（`task_schema`） | 履约产出（`result_schema`） |
| **复合组件** | 父节点喂给它的东西 | 它的末跳的产出 |

**于是「盒」与「复合组件」的区别只剩一件事**：
盒额外带**履约级**的东西（产出契约 / 判据 / 例外 / 政策 / 度量）——
这正是总稿 §3.2 的那张表 ✓。

**`external` 的含义是「本作用域的输入」**：
在盒里是投料，在复合组件里是父节点给它的东西。
**同一个词，一个意思**（作用域内相对）✓。

### 4.2 递归版的检查

现有检查在「一层链」上的样子，和递归版的对照：

| 检查 | 一层链 | 递归版 |
| --- | --- | --- |
| C1 每跳有实现 | 每个 op 都要有 handler | **每个叶子**都要有；复合节点没有 handler（§3.3） |
| C2 数据来源自洽 | `input_from` 指向真实 op | 同左，**在各自作用域内**判定（子链里的 `input_from` 不许指向作用域外） |
| C3 入口吃的就是投料 | 入口的 input 必须能吃下投料 | **每个作用域**各判一次（复合组件的入口要能吃下**它的输入**，而它的输入要与父节点给的东西相容） |
| C4 执行顺序上的数据形状 | 上一跳的产出喂得进下一跳 | 同左，**在各自作用域内** |
| C5 唯一入口、无孤岛、无环 | 整条链 | **每个作用域**各判一次（子链里也必须有唯一入口、不能有孤岛、不能成环） |
| C10 末跳产出 == 产出契约 | 末跳 == `result_schema` | **每个作用域**各判一次（盒：末跳 == `result_schema`；复合组件：末跳 == 它的 `output`） |

**关键点**：这些检查**不是新写的**，是把今天写死在一个作用域里的逻辑
**抽成一个「判一个作用域」的函数，然后递归调用** ✓
——「同一份判定只放一处」（总稿那条纪律）。

### 4.3 一个作用域的入口与末跳

- **入口**：作用域内 `input_from == "external"` 的那个（恰好一个）
- **末跳**：作用域内 `next` 为空的那个（恰好一个）
- 复合组件的**入口**吃的是**父节点喂进来的东西**；
  复合组件的**末跳的产出**就是**这个复合组件的产出** ✓

### 4.4 复合组件的形状怎么判

复合组件 `X`（在作用域 S 里）与它的作用域 X：

| 判什么 | 规则 |
| --- | --- |
| X 的输入 | 父节点喂给 X 的东西，必须喂得进 X 的入口跳 |
| X 的产出 | X 的末跳的产出 == X 声明的 `output`（C10 的递归版） |
| X 的孩子 | X 的作用域自己有唯一入口、唯一末跳、无孤岛、无环 |

### 4.5 三个「由子节点推导」的属性

复合组件的这三个属性**不自己说了算**——**子节点说了才算**，
否则父与子会给出两个答案（两份事实）。

| 属性 | 推导规则 | 为什么 |
| --- | --- | --- |
| `leaves_artifact` | **任一子节点声明了就是** | 孩子在真实世界里留了东西，父节点不可能「没留」 |
| `idempotency.mode` | **任一子节点是 `forbidden` → 父也是 `forbidden`**；否则**全部子节点都是 `required` → 父是 `required`**；再否则 `optional` | **父不能比子更宽松**：子声明了「不许重放」，父却声明「可重放」→ 重放会重做子节点的副作用 |
| `timeout_seconds` | **子节点的预算不得大于父节点的**（父有预算时） | 子预算比父大 → 子预算**永远不触发**（声明了却没人执行） |

**推导是机械的**（装配期算出来），
**不推导的写法装配期就报错**（比如父声明 `leaves_artifact=False` 而某个子声明了 `True`）✓。

### 4.5.1 预算：**剩余截止时间向下传**，不是「各算各的」

**只比「子预算 ≤ 父预算」是不够的**：

```text
父预算 10s
├─ 子链 A 预算 8s
└─ 子链 B 预算 8s
```

配置合法（A ≤ 10、B ≤ 10），**总耗时却可以到 16s**——
父的 10s 预算**没有约束到子链**。

**所以预算是「剩余截止时间」，不是一个可以各自独立的数**：

| 规则 | 说明 |
| --- | --- |
| **一个截止时刻，一路往下传** | 父作用域开始时算出 `deadline = 开始时刻 + 预算`；进入子作用域时传的是**同一个 deadline**（不是「子链自己的预算」） |
| **启动子节点前检查** | 剩余时间不够 → 不启动这一段（和「每次尝试之前检查」同一口径） |
| **每次重试前检查** | 同上：重试也是「再开一次工作」 |
| **子链自己声明的预算** | 只能**更紧**：`child_deadline = min(父传下来的 deadline, 子链开始时刻 + 子链预算)` |

**判据是「距截止时刻还剩多久」，不是「这一段自己花了多久」**——
这样父的预算才是**真约束**，而不是一个跟子链各自计时的数字。

**为什么必须这么定**：预算是「不再开新工作」的闸。
闸要真的挡住事，就得判**同一个截止时刻**；
各算各的话，父的闸形同虚设（而读者会以为它在守着）。

### 4.5.2 幂等键：父的 `idempotency.key` 从哪来

`required` 这一档**必须带 key**（`core/beeline_models.py` 的 `Idempotency` 校验：
`mode=required` 而没有 key → 装配期就拒）。
所以「所有孩子都是 `required` → 父也是 `required`」这条推导**推不出一个合法的父**。

**两条路，必须选一条**：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A（采用）** | **父不推导 `required`**：父的幂等档取**子节点里最严的那一档**，且**只有当所有子节点都 `required` 且它们的 key 相同**时父才是 `required`（key 取那个共同的 key）；**key 不同 → 装配期报错** | 组合出来的复合组件多半不是 `required`（各孩子的 key 本来就不同）——这是**如实**：它本来就不保证重放同结果 |
| B | 父自己声明 key，与孩子的 key 无关 | 父的 key 成了**第二份事实**（孩子的 key 与它无关）→ 两份事实迟早不一致 |

**采用 A**：理由与「宿主声明要有单一真源」同族——
**父的 key 只能来自孩子的 key**，不能另起一份。
而「孩子的 key 不一样」这件事**如实报错**（装配期），
比默默给父造一个假 key 好。

**注意 `required` 现在还没有消费点**：
跨履约的去重台账**还没做**（`Idempotency.mode=required` 现在只是一句承诺）。
所以这条规则现在只影响**声明的合法性**，不影响运行行为 ✓
（总稿 §3.3 说「不迁成插件」的理由同源）。

### 4.6 op_id 全树唯一

今天 op_id 在**盒内**唯一。递归之后，**子链里的 op_id 与外层可能撞**——
而 `task_run.operations` 是个**平铺的 dict**（按 op_id 索引）。

**决定：op_id 全树唯一**，装配期查重 ✓。

**为什么不用「路径化」的 op_id**（`outer/inner`）：
那会改掉 op 记录与 op_trace 的形状（下游、看板、导出都在读它），
而这一批的目标是**加能力**，不是**换记录格式** ✓。

## 5. 运行期：子链怎么跑

### 5.1 执行器变成递归的

今天执行器是「一条链一个循环」。递归之后：

```text
执行一个作用域（链）：
  取入口节点
  循环：
    节点是叶子 → 跑 handler（重试在这一层）
    节点是复合 → **递归执行它的子作用域**，子作用域的产出 = 这个节点的产出
    产出喂给下一个节点
```

**重试仍在「叶子」这一层** ✓（总稿 §4.6.1 的两层结构不变：
一次调用 = 一次执行 + 它的所有重试；**子链是另一次调用**）。

### 5.2 步数上限要算整棵树

今天：`max_steps = len(beeline.operations) * (MAX_OP_ATTEMPTS + 1)`。
递归之后：**节点总数**（整棵树）才是分母——
用外层的节点数算，内层的重试会被外层的上限判死
（**机制自己把机制掐了**，那条教训）。

### 5.3 记录：复合节点也有记录

- **复合节点本身**有一条 op 记录（status / output = 子作用域的产出）
- **它的子节点**各有一条
- 事件流里能看到嵌套：`op_start(A) → op_start(B) → op_finish(B) → op_finish(A)` ✓

### 5.4 产出的方向：**父 ⊆ 子**

总稿 §3.1 的规则：**父承诺的必填字段，必须由内部执行结果保证提供**。

M8 的实现取**更严的一条**：

> **每个作用域的产出 schema 必须与末跳的产出 schema 相同**（schema id 相等）。

这比「父 ⊆ 子」严，但**不需要输出映射** ✓——
本批不做映射（§2.2），所以只能取严的这条。
「父 ⊆ 子 + 输出映射」是 M8.1 的事（映射做完才能放宽）。

### 5.5 失败怎么往上走

子链里任何一跳失败 → **那个作用域失败** → 父作用域失败 → 履约失败 ✓
（失败原因逐层带上去，读者看得到是哪一跳）。

### 5.5.1 「现场有残留」：**按本次的执行记录判**，不按静态声明判

**两件事必须分开**：

| | 是什么 | 用来干什么 |
| --- | --- | --- |
| **`leaves_artifact`（声明）** | 这一段**可能**在真实世界里留下东西 | 决定**能不能重放**、要不要禁止重试 |
| **本次是否真的留了东西（事实）** | **哪些后代真的跑完了**，且它们声明了会留东西 | 决定履约落 `failed` 还是 `partially_completed` |

**为什么不能用声明代替事实**：

```text
复合节点 X = [A（写库）, B（读库）]
```

| 情形 | 事实 | 该落的状态 |
| --- | --- | --- |
| **A 失败**，B 还没跑 | 写库**没发生** | `failed`（什么都没留下） |
| **A 跑完了**，B 失败 | 写库**已经发生** | `partially_completed`（现场有残留） |

两种情形**声明一模一样**（`leaves_artifact=True`），
但结论**完全相反** ✗ → 所以判据必须是**本次的执行记录**：
**已跑完（`completed`）且声明了会留东西的后代**。

**现有的 runtime 已经是这么判的** ✓：
`_end_unfinished` 数的是「**已完成的跳**里有没有声明了留产物的」
（判的是「这一跳跑完了 + 它声明会留」，
不是「整棵树里有没有一个声明会留的」）——递归之后这条**原样沿用** ✓。

**状态只由最外层落**：
子作用域失败 → 一路往上抛 → **履约层（最外层）落一次状态**。
子作用域**不自己落** `partially_completed`——
状态机是全局的，子作用域落状态会跟外层的落法打架
（内层落完，外层再落一次 → 非法转移）。

**要说准的边界**（总稿 §4.6.7 已经写过一次）：
`leaves_artifact=True` 是「**这一跳可能产生副作用**」的声明，
**不代表副作用真的发生了**。runtime 现有判法是「已完成的跳里有没有声明了留产物的」
——判的是**声明**，不是**事实**。
要判事实得靠**真实副作用追踪**，那是能力层的事，不在本方案范围。

## 6. 插件：挂在任意节点

### 6.1 宿主种类多一种

```text
HostKind = "op" | "composite" | "box"
```

- `op` —— 作业组件（一跳）
- `composite` —— 复合组件（盒内可嵌套）
- `box` —— 盒子（整盒）

**为什么复合组件算一种宿主、而不是复用 `op`**：
它们的**扩展点契约不一样**——
作业组件的 `op.before` 看的是「这一跳的输入」，
复合组件的 `op.before` 看的是「这一整段的输入」。
**同一个词两套语义 = 读者按名字猜、猜错就按错的找**（总稿 §1.1.3）。

### 6.2 op 级扩展点同时支持两种宿主

`op.before` / `op.after` / `op.around` 的 `host_kinds` 变成
`("op", "composite")` ✓ —— **同一套语义**：

| 扩展点 | 挂作业组件 | 挂复合组件 |
| --- | --- | --- |
| `op.before` | 这一跳执行前 | **这一整段**执行前 |
| `op.after` | 这一跳执行后 | **这一整段**执行后 |
| `op.around` | 包住这一跳 | **包住这一整段** |

**视图形状不变** ✓：
`op.before` 看 `input`；`op.after` 看 `input` + `output`；
`op.around` 看 `input` + `call` + `op`（宿主声明）。
对复合组件来说，`input` / `output` 就是**这一整段的输入与产出** ✓。

### 6.3 「这一跳」的措辞要改

插件的提示词、报错、文档里说「这一跳」时，
挂在复合组件上的插件看到的是「**这一段**」。
**措辞不统一 = 插件作者按「一跳」理解，然后写错**。

## 7. 批次拆分

| 批 | 内容 | 行为变化 | 验收 |
| --- | --- | --- | --- |
| **M8-A** | **core 侧**：`CompositeComponent` + `children` + 把 C1–C12 抽成「判一个作用域」并递归调用 + beeline 的递归节点 | **无**（没人声明复合组件） | 全部盒子的声明与作业路线导出**归一后逐字相同**（§9.1 的新增字段归一）+ 每条新校验配一条**会红**的守卫 |
| **M8-B** | **runtime 侧**：执行器递归跑子作用域 + 记录与事件流的嵌套 + 插件宿主第三种 kind + 三个「由子节点推导」的属性 | 新能力 | 既有盒子**零影响**（逐项差分）+ 递归执行的守卫 |
| **M8-C** | **真用上**：把一只盒子的链真的拆成两层 | 新能力 | **待拍板**：哪只盒子、怎么分组是业务判断（候选：设计盒的「生成腿 + 打包腿」） |

**M8-C 为什么单独一批**：分组是**业务判断**——
「哪些跳算一段」得由懂那只盒子的人定，机制不该替业务定。
机制先落（无影响），业务再挑。

## 11. 一轮 CR 补掉的三处（2026-11-19）

这份稿子定稿后过了一轮外部评审，**三处语义缺口当场补齐**（都在上面）：

| 原来写得不够 | 现在 |
| --- | --- |
| 预算只说「子预算不得大于父预算」→ 父预算 10s、两段各 8s 合法，总耗时却能到 16s | **预算是「一个截止时刻往下传」**（§4.5.1）——父传子同一个 deadline，判的是「还剩多久」 |
| 残留按 `leaves_artifact` **静态聚合** → 「写库那跳失败」与「写库完成后下一跳失败」结论相同 | **按本次的执行记录判**：哪些后代**真的跑完了**且声明了会留东西；状态**只由最外层落**（§5.5.1） |
| 父的 `idempotency.key` **从哪来**没说 → 「孩子都 required → 父 required」推不出合法的父 | **父的 key 只能来自孩子的 key**；孩子 key 不同 → 装配期报错，不默默造假 key（§4.5.2） |
