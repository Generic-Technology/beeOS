# beeOS 架构升级：盒子脚手架化

> 这份文档是**定稿**，不是提案。里面的每条决策都已经在 2026-11-03 拍过板，
> 写在这里是为了让实施过程有唯一的依据——实施途中如果发现某条要改，
> **先改这份文档，再改代码**。文档和代码不一致时，文档是待改的那一方。

## 0. 一句话

把「加一只盒子 = 复制一份模板再改」变成「按协议填组件，**装配期就报错**」。

## 1. 现状（2026-11-03 实测）

| 事实 | 证据 |
| --- | --- |
| 新建盒子是**复制**不是组装 | `scripts/new_box.py` 里 7 个内联模板，产出约 380 行样板，业务只占 10–20% |
| 业务真散在样板之间 | `boxes/` 下约两万行 Python，样板与业务交织 |
| core 已有**形状**，没有**装配** | `core/models.py`（声明）、`core/beeline_models.py`（作业路线）都在，但没有把它们组装起来的机制 |
| 盒子发现是显式字典 | `kanban/trigger.py` 的 `BOX_REGISTRY` |
| 装配期能查的错，今天靠**事后**发现 | `tests/test_box_standard.py` 是今天才发现「判据读不到字段」「例外永远不触发」的地方 |

**「真正的升级在哪」**：不是「少写样板」。样板少写几百行，review 时眼睛一样累。
真正的升级是——**装配期就报错**：一只盒子在还没被注册、还没被投料之前，
它的声明自相矛盾（判据读不到字段、例外永远不触发、op 链接不上）就已经被拒。

## 2. 五条拍板决策（2026-11-03）

1. **组合式（协议式）插件**，不用继承式。
   盒子之间的差异是**形状**（几跳、什么契约），不是**行为**（怎么做）。
   继承式会让「基类一改，全跟着改」——12 只盒子同时被一次重构掀翻。
2. **core 只定协议，不定跳数。**
   票据盒 2 跳、学习盒 4 跳、设计盒 7 跳，形状本就不同。
   core 若内置一个「默认三跳形状」，就等于把最多数盒子的形状硬塞给少数盒子。
3. **保留 `boxes/` 下的 7 文件分区**（内容变薄，不压扁）。
   schemas（契约）/ definition（声明）/ beeline（op 链）/ runner（实现）/
   measure（指标）各有**真实的信息分区**。压成 500 行的单文件，review 会变难。
4. **显式注册，不扫描目录。**
   自动扫描会把「仓里有哪些盒子」从**代码事实**变成**运行时事实**——
   删掉一个目录盒子就消失了，而没人收到通知。注册表是显式的，改动会进 diff。
5. **全部迁移。**
   一次迁一只，每迁一只立刻验，全程不留两套规矩并行到最后。
   （这条与「先问建议」相反，是拍板结果——照办。）

## 3. 协议

### 3.1 盒子提供什么

盒子提供**数据**，不继承任何东西。

- **`Component`** —— 一跳。声明 `op_id` / `input_from` / `input` / `output` /
  `next` / `handler` / `idempotency` / `leaves_artifact`。
- **`BoxDeclaration`** —— 这只盒子是什么。声明 id / 归属（域、价值流、角色、接线）/
  投料入口 / 产出契约（schema、判据、例外、形态、成熟度）/ 作业路线标识 / 政策 / 度量。

### 3.2 core 提供什么

- **`assemble(declaration, components, *, schemas, handlers=None)`** —— 组装 + 校验。
- **`AssembledBox`** —— 装好的四件套：`definition` / `beeline` / `runner` / `report`。
- **`AssemblyError`** —— 装配没过。**每一条问题都带能修它的材料**
  （是哪个 op、哪个 schema、现在是什么、应该是什么）。

### 3.3 校验清单

这些校验**今天**是靠 `tests/test_box_standard.py` 事后发现的。
它们要搬进装配期——同一批检查，一个在运行时，一个在写代码时。

| # | 校验 | 不这么做会怎样 |
| --- | --- | --- |
| C1 | 每个 op 有 handler | 履约跑到那一跳才炸（`no handler for op_type`） |
| C2 | `input_from` 指向的 op 存在，且它的 `output` == 本 op 的 `input` | 声明的数据来源落空，产出形状对不上 |
| C3 | 恰好一个入口 op（`input_from="external"`），且它的 `input` == `task_schema` | 投料的形状跟第一跳期待的形状不是一回事 |
| C4 | `next` 边指向真实 op，且目标 `input` == 本 op `output` | runtime 沿 `next` 喂数据，喂的形状不是下一跳声明的形状 |
| C5 | op 图无环、且没有孤岛 op（都能从入口走到） | 链断在某处，那一跳永远不跑，也不报错 |
| C6 | op 的 `input`/`output` 都是本盒声明过的 schema | 引用一个不存在的 schema id，没有任何校验会响 |
| C7 | `task_schema` / `result_schema` 都存在 | 引用落空 |
| C8 | 每条判据的 metric 都在产出 schema 的字段里 | 判据永远读不到值 → 恒过（假绿灯）或恒红 |
| C9 | 每条例外条件是 `field op value` 三段式、字段在产出 schema 里 | 规则写在那里，**永远不触发**（安静地没做） |
| C10 | 末跳（无 `next` 的 op）的 `output` == `result_schema` | 产出的形状跟声明的产出契约不是一回事 |
| C11 | `maturity="live"` 的盒子至少有一条判据 | 零判据被判成「全过」——「看起来成功，其实什么也没验」的谎 |
| C12 | `subject_ref_field` 在投料 schema 里；`subject_ref_*` 必配 `subject_kind` | **声明了却拿不到** → 归档时这条履约记录归不到任何工作单元 |

C1–C12 全部在现有全部已注册盒子上成立（见 §3.5）。
**它们不是凭空定的规则，是这批盒子的真实形状。**

### 3.4 条件语法的归属

C9 用**被验者自己的解析器**（`runtime/acceptance.py` 的 `condition_parts` /
`condition_fields`），不另写一份——写两份就会漂，漂了就等于「验的不是那个」。

但装配器在 `core/` 里，而条件解析在 `runtime/` 里。
**core 是底层，不该反向依赖执行层。** 所以条件语法搬进 `core/conditions.py`，
`runtime/acceptance.py` 从那里取并继续导出——**一处定义，多处引用**，
现有 import 路径不用改。

### 3.5 协议被现有盒子证明过

写装配器之前，先拿现有全部已注册盒子跑了一遍探针，逐条验 C2/C3/C4/C6/C8/C9/C10：

```
.venv/bin/python -m pytest tests/test_scaffold.py -q
```

结果：**全部通过，0 条不成立**。

这条证据很关键——它说明 §3.3 的校验不是凭空定的规则，而是**这批盒子的真实形状**。
如果哪条校验在现有盒子上不成立，那要改的是**协议**，不是盒子。

这条探针已经变成常驻守卫（`tests/test_scaffold.py` 里那条
「拿全部已注册盒子过一遍装配器」），所以它不是一次性验证——
**协议改了、盒子加了，它都会响**。

## 4. 文件分区映射（保留 7 文件，内容变薄）

| 文件 | 装什么 | 变薄成什么样 |
| --- | --- | --- |
| `definition.py` | `BoxDeclaration` | 去掉 pydantic 字段名重复、去重样板 |
| `beeline.py` | `Component` 列表 | 不用手写 `Operation` / `NextRef` / `Bee` 的样板 |
| `runner.py` | handler 实现 + handler 表 | 不用手写 `HandlerRunner` 装配 |
| `schemas.py` | 业务 schema | **基本不变**（契约是业务真） |
| `measure.py` | 指标采集 | 没有指标就不建这个文件 |
| `README.md` | 这只盒子是什么 | 内容变薄 |
| `__init__.py` | **装配 + 导出** | 见下 |

**`__init__.py` 是盒子的清单，也是装配发生的地方**：

```python
ASSEMBLED = assemble(DECLARATION, COMPONENTS, schemas=ALL_SCHEMAS, handlers=MODEL_HANDLERS)
WMS_DESIGN_BOX = ASSEMBLED.definition
WMS_DESIGN_BEELINE = ASSEMBLED.beeline
```

**装配期就报错**——声明自相矛盾的话，这一行就抛 `AssemblyError`，
带着「是哪个 op、哪个 schema、现在是什么、应该是什么」。

装配器住在 `core/`，而 `core/` 是底层，**不反向依赖 `runtime/`**。
所以 core 交出去的是**协议数据**（声明 / 作业路线 / 实现表），
执行器由盒子的 `runner.py` 那行接到 runtime 上：

```python
RUNNER = HandlerRunner(MODEL_HANDLERS, owner="wms_design_box")
```

**每只盒子都从包导出 `get_definition()` / `get_beeline()`**——
包是盒子的公开面，别的模块一律从包拿，不去摸 `definition.py`。

**样板里的「为什么」注释原样保留。**
压成一行 = 静默复制，比现在更糟——那些注释是踩坑记录，不是装饰。

## 5. 迁移计划

**顺序：先拿最难的一只探路。**

1. **`wms_design`**（跳数最多、判据最多、例外最多、还有 ref 交接）
   ——它能装下，协议就够用；装不下说明协议漏了东西，
   **现在暴露比迁完所有盒子再发现便宜得多**。
   - ✅ **已迁（2026-11-03）**：7 跳 / 8 判据 / 5 例外 / ref 交接全部走新协议。
     差分验证：迁移前后**声明 + 作业路线逐字节相同**，
     **真跑一次链路的产出也逐字节相同**。
2. 学习域 4 只 → 票据 → WMS 其余。
3. 每迁一只：跑全量 + 真跑一次链路 + 对比迁移前后的产出。
4. 最后删旧路径，**不留兼容层**。

**迁移期的两套路径并存是计划内的**，控制手段是三条守卫同时上：

- 一只盒子**不许混着写**（不能同时出现 `BoxDeclaration` 和 `BeeBoxDefinition`）
- 走了新路径的盒子**必须真的在装配**（声明写在文件里没人装 = 没迁移）
- 「新盒子必须走装配器」——由**脚手架模板**保证（`scripts/new_box.py` 改造后
  生成的盒子直接就是新写法），而不是靠人记着

**差分测试**：迁移前录一份产出，迁移后重跑比对。
无 LLM 腿的盒子逐字节比；有 LLM 的比结构与判据结论（LLM 有采样，逐字节比必然假红）。

### 5.1 差分验证怎么做（已跑通）

```bash
# 迁移前：在上一个 commit 的隔离 worktree 里导出
python -c "dump 声明 + 作业路线 → JSON"
# 迁移后：主仓导出同样的东西
diff -u before.json after.json     # 必须完全一致
```

真跑链路同理：同一个投料、同一份 store，比对 `status` /
`acceptance_status` / `result` / `acceptance`。

**空文件不算「一致」**——第一次跑差分时两边都 dump 失败，
`diff` 对着两个空文件说「完全一致」。所以比对前必须先断言体积非空。

## 6. 风险与保险

| 风险 | 保险 |
| --- | --- |
| 两套路径并存，规矩漂移 | 两条守卫：新盒子必须走新路径 + 旧路径清单写死 |
| 协议不够用 | 用 `wms_design` 探路，**先暴露再迁** |
| 迁移改错业务 | 差分测试（迁移前后产出比对） |
| 核心改动影响线上 | 一次迁一只，每只立刻验；迁移不碰 `runtime/` 的执行逻辑 |
| 装配器把业务知识拉进 core | 装配器只认协议；`core/` 不出现任何盒子名 / op 名 / 业务词（已有守卫） |

## 7. 不做什么

- **不扫描目录发现盒子**（决策 4）。
- **不内置「默认几跳」**（决策 2）。
- **不把 7 个文件压成 1 个**（决策 3）。
- **不做继承式基类**（决策 1）。
- **不留兼容层**：迁完就删旧路径。
- **不在 `core/` 里写任何业务词**。

### 7.1 探针脚本

协议探针（跑完 C2/C3/C4/C6/C8/C9/C10）落成 `tests/test_scaffold.py` 里的
一条守卫：**拿全部已注册盒子过一遍装配器**。
所以探针不用另存一份脚本——它已经变成常驻守卫。

## 8. 文档与代码的关系

- 这份文档 = **决策与协议**。
- `core/scaffold.py` = **协议的代码**。
