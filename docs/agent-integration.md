# 对外接入面：链路、边界与分期

> **这是设计稿，不是定稿。** 本文定的是**对外接入面**的概念与边界；
> 仓库现状以 [仓库 README](../README.md) 为准。
> **状态**：v0.1 草稿 · 修订中
> **日期**：2026-11-25
> **定位**：**接入面** = 谁调 BeeOS、凭什么调、调完怎么算。
> 本稿以「通用外部 agent」（Codex / Claude Code / 千问办公 / WorkBuddy / 豆包 …）
> 为主要调用方举例，但**接入面服务的不止 agent**——
> 任何外部调用方都走这一层，agent 只是其中一种。

---

## 0. 一句话

**可行。** 但「可行」的部分不在「接一个 agent」——
接一个 agent 只是**换一种投料方式**（今天已有 `originator` 字段为此预留）；
真正的工作量在**补三个机制**：

| # | 机制 | 不补会怎样 |
| --- | --- | --- |
| 1 | **身份与授权** | 任何调用方都能自称「人」来放行一次验收失败的履约 |
| 2 | **幂等与持久化执行** | agent 自动重试 → 同一次投料跑两遍 → 目标对象被写两遍 |
| 3 | **链级编排** | agent 每次都得自己决定「下一跳投哪只盒」，且每次都可能投错 |

这三个机制**在今天就缺**，不是接 agent 才缺。
接 agent 只是把「一次手误」变成「每天自动发生」。

## 1. 链路形状

### 1.1 四层

```text
外部 agent（Codex / Claude Code / 千问办公 / WorkBuddy / 豆包 …）
      │  投料：意图 + 输入 + 幂等键
      ▼
BeeOS（编排层 + 平台能力层）
      │  选盒、接力、链状态、幂等、身份、观测
      ▼
beeBox（履约单元：契约闸 → beeline → 验收 → 例外 → 证据）
      │  op 内部读写目标对象
      ▼
目标对象（Shopify API / WMS 仓库 / 文件系统 / 第三方 HTTP …）
```

### 1.2 三层视图也是对的

`Agent → BeeOS → 目标对象` 是**系统级视图**：展开 BeeOS 内部才出现 beeBox、
Component 和目标适配。两种画法描述的是同一件事：

- **三层**回答「谁对谁负责」（BeeOS 提供统一入口，beeBox 提供具体业务契约）；
- **四层**回答「一次履约的职责落在谁身上」。

**本文用四层**，因为接 agent 时真正要定的是职责归属——
三层图里看不出「写目标对象」这件事该由谁负责。

### 1.3 职责分层 ≠ 部署分层

四层**不是四个部署单元**。实际形态是**一个 Python 包 + 一个端点**：

```text
agent ──HTTP / CLI / MCP──▶ BeeOS（一个进程）
                            ├── 编排层：这条链走到哪、下一步投哪只盒
                            ├── 盒 A（beeBox）：单次履约的契约与判据
                            ├── 盒 B（beeBox）
                            └── 目标对象（只在盒内某一跳被读写）
```

外部 agent 看到的**始终是一个入口**。
把四层读成四个服务，等于凭空多出三个网络跳转和一份分布式一致性难题。

### 1.4 边界判据

> **beeBox 不该知道链的存在；BeeOS 层不该知道判据的内容。**

越界就说明分层错了：

| 越界例子 | 为什么是错的 |
| --- | --- |
| 盒子自己去查「上游是哪条链的第几跳」 | 链是编排者的知识；盒子知道了就没法被复用 |
| 编排层里出现「这条判据过不过」的业务判断 | 判据是盒子的契约；编排层知道了，换盒就得改编排 |
| 盒子里出现「调用方是谁、能不能写」 | 授权是平台能力；盒子知道了，同一只盒子在不同调用方下行为就不一样 |

### 1.5 目标对象的位置

`beeBox → 目标对象` 这条箭头在链路上画出来没问题，但实现上它是**盒内的一跳**，
不是「盒调用一个外部服务」。区别很实际：

- 写目标对象必须过**盒内声明的闸**（例：店铺实验盒的 `apply` 与
  `write_scope`，见 `boxes/shopify_acquisition_experiment/schemas.py`）；
- **外部 agent 不能直接调目标对象 API**——理由见 D2。

## 2. 现状盘点（2026-11-25 实测）

### 2.1 已经具备

| 能力 | 现状 | 出处 |
| --- | --- | --- |
| 投料入口 | `trigger_task(box_id, task_type, payload, store, originator, handoff, chain_ref, chain_kind)` | `kanban/trigger.py` |
| 多触发源 | `originator` 参数已存在（默认 `"kanban.web"`）——**设计上早就预留了「谁投的料」** | `kanban/trigger.py` |
| 链归属 | `chain_ref` / `chain_kind` 随履约落盘 | `runtime/models.py`、`runtime/store.py` |
| HTTP 面 | `POST /api/trigger`、`POST /api/structure`、`POST /api/runs/{id}/decision` | `kanban/web.py` |
| 发现面 | `box_manifest()` 的 docstring 明写「盒子的完整自描述——它作为独立 API 单元时对外的全部契约」 | `kanban/trigger.py` |
| 盒间接力 | `handoff_payload()` 按声明里的边接产出，不是抄的第二份 | `fulfillment_scopes/__init__.py` |
| **链序可推导** | `derive_wiring()` 从协作边界声明的交接边做拓扑排序——**推导出的 WMS 环序与 `scripts/run_chain.py` 实际跑的六步一致** | `core/wiring.py` |
| **每跳跑哪个 task** | `Edge.to_task`（下游多 task 时必填，单 task 唯一推断）+ `Edge.via`（投料通道名） | `core/models.py` |
| 升级闭环 | queen 判 `escalate` → `waiting_external` → `resume_waiting_run` 等一个说法 | `runtime/queen.py`、`runtime/resume.py` |
| 「已接受、还没开跑」的状态 | `triggered` 是 TaskRun 的初始状态，转 `running` 才真开跑 | `runtime/models.py` |
| 干跑闸 | `apply` 字段 + 写权限环境变量，两道闸分开 | `boxes/shopify_acquisition_experiment/schemas.py` |
| 手写编排原型 | 六跳的 WMS 链手写在一个脚本里——**但它的顺序与声明推导一致**，所以它能被声明投影替换掉 | `scripts/run_chain.py` |

**结论**：地基比想象的厚。**不需要新造「盒子是什么」「怎么投料」「产出长什么样」
「链怎么排」**——这四件事都已经是对外契约，或者已经能从声明推导出来。
真正要新建的只有**执行状态**那一半（见 D5）。

### 2.2 缺什么

| 缺什么 | 现状 | 后果 |
| --- | --- | --- |
| **认证** | Web 看板无认证（README 已声明） | 不能暴露给外部 agent |
| **调用方身份** | `decided_by` 来自请求体（`kanban/web.py`） | 任何调用方都能自称「人」放行 |
| **跨履约幂等** | op 内有重试策略，但**跨履约的去重台账还没做**（`core/beeline_models.py` 的注释写得很直白） | agent 重试 = 重复写目标对象 |
| **异步执行** | 任务同步执行，存储是本地 JSONL | 一条长链跑几十分钟，agent 侧必然超时 |
| **链的执行状态** | 链**结构**已能从声明推导（`core/wiring.py`），但**状态**没有实体——`chain_ref` 只是记录上的一个字段 | 编排知识留在 agent 脑子里，换个 agent 就断 |
| **公共契约版本化** | `/api/*` 的返回形状是给前端画页面用的 | 对外一发布，形状就成契约，改不动了 |
| **MCP / 稳定 CLI** | 全仓无 MCP | 非 shell 环境的 agent（豆包、千问办公）没有原生接入面 |

## 3. 六个决策

### D1 推理分工：唯一的是「结论」，不是「推理次数」

**问题**：外部 agent 会推理，盒内也会调模型（`runtime/llm.py`）。
直觉上这是「两份事实」。

**决策**：**不要求全系统只有一处推理**。
真正要唯一的，是**本次履约采用的输入、契约和验收结论**——这三样一份履约里只能有一份。

| 谁 | 负责什么 |
| --- | --- |
| 外部 agent | 意图层：理解需求 → 选盒/任务类型 → 备输入 → 在被问到时给个说法 |
| beeBox 内 | 领域层：票据识别、需求抽取、流量诊断等领域判断 |

**理由**：盒内做票据识别、外部 agent 做任务规划，职责本来就不同，
硬要合成一处反而逼出「谁做抽取」这种无解的争论。

**附带一条**：自然语言与结构化输入**可以并存**，但要守一条——
**一份输入只解释一次**。同一请求不许既被 agent 解释、又被 BeeOS 解释；
转换结果必须留痕。

**落点**：投料接口要么收结构化载荷（agent 已经理解好的），
要么收自然语言（BeeOS 理解），**一次只走一条路**；另一条路是兜底，不是并行。

### D2 唯一写入口：靠凭证隔离，不靠约定

**问题**：把目标 API 放进 op，**并不能自动阻止绕过**。
绕过是代码边界和凭证边界问题，不是结构问题。

**决策**：**写目标对象的动作只发生在盒内 op 里**，且：

1. **外部 agent 拿不到目标对象的写凭证**——这是唯一真正拦得住绕过的边界。
   约定（"agent 不许直接调"）拦不住任何东西。
2. 写操作要过**盒内声明的闸**（`apply` / `write_scope` / 字段白名单）。
3. `originator` 只标记来源，**不证明身份**（见 D3）。

**理由**：`SHOPIFY_ALLOW_WRITES` 这类环境变量就是凭证隔离的原型——
它已经在仓库里了，接 agent 时要延续这个思路，而不是新增一套。

### D3 身份与授权前移：`decided_by` 由认证身份确定

**问题**：现在审批接口里的 `decided_by` 取自**请求体**。
也就是说调用方自己说「我是 human」——那么「agent 回答升级问题」和
「agent 有权人工放行」就是同一件事，而它们不该是。

**决策**：

| 角色 | 能做什么 |
| --- | --- |
| 调用方（agent） | 回答事实性问题（补充信息、提供素材） |
| 认证身份 | 决定放行 / 拒绝（`decided_by` 从认证身份来，不由请求体来） |
| 盒内判据 | 决定这次履约本身合不合格 |

**理由**：「人放行了」和「判据过了」是两件事——这句话仓库里已经写着了
（`kanban/web.py` 的审批分支注释），但**取值的来源**没跟上。

**顺序要求**：**授权必须在任何对外写能力之前**。
先给 agent 投料能力、后补认证，等于先开门再装锁。

### D4 幂等与持久化执行：四件事一件都不能少

**问题**：「传一个幂等键，重复提交返回原来的 run_id」只是**接口表现**。

**决策**：

| # | 要求 | 说明 |
| --- | --- | --- |
| 1 | **原子性** | 同一幂等键的并发请求只能创建**一次**履约 |
| 2 | **冲突拒绝** | 同一键携带**不同载荷 / 不同目标 / 不同契约版本** → 拒绝，不复用 |
| 3 | **先持久化再执行** | 接受任务时先把计划落盘，再开始跑 |
| 4 | **可核对** | 外部写成功、服务却中断时，能核对目标对象状态，避免盲目重做 |

**为什么第 3 条紧跟第 4 条**：没有「先落盘」，第 4 条无从谈起——
进程一重启，谁也不知道上次写到哪了。

**状态语义**：**不需要新增 `queued` 状态**。现有 `triggered` 就是
「已接受、还没开始执行」，转 `running` 才真开跑（`runtime/models.py`）。
把它对外暴露成 `queued` 即可，**别造第二个同义状态**。

**为什么这条是硬要求**：agent 会自动重试（超时了重发、网络抖了重发）。
今天的 op 重试策略管的是「这一跳传输失败要不要再试」，
**管不了「同一次投料被提交两遍」**——这两件事不是一回事。

### D5 链级执行计划：**声明投影 + 执行状态**

**问题**：`chain_ref` 能把记录归组，但回答不了「下一步该执行什么」。

**先纠正一个想当然**：编排层**不需要另写一份链定义**。
链的结构那一半，仓库里**已经能从协作边界声明推导出来**：

| 结构要素 | 从哪来 | 现状 |
| --- | --- | --- |
| 链序（谁在谁前面） | `derive_wiring()` 对交接边做拓扑排序 | ✅ 已有（WMS 推导结果与实际跑的六步一致） |
| 每跳跑哪个 task | `Edge.to_task`（多 task 必填，单 task 唯一推断） | ✅ 协议里已有这个位置 |
| 每跳的投料通道 | `Edge.via` | ✅ 已有 |
| 投料怎么组装 | `handoff_payload(scope_id, to_box, sources)` | ✅ 已有 |

**所以执行计划 = 声明投影（结构）+ 执行状态（动态）。**
新建的只有**状态那一半**：每步的 `task_run_id`、状态、等待条件、推进责任，
以及一次链本身的持久化（今天 `chain_ref` 只是记录上的一个字段，**没有「计划」这个实体**）。

**决策**：把两个能力分开：

| 能力 | 回答什么 | 谁调 |
| --- | --- | --- |
| **看链历史** | 这条链发生过什么 | 人 / agent（只读） |
| **驱动链前进** | 下一步做什么、谁来做 | BeeOS 编排层 |

**计划草案**（结构字段由声明投影给出，这里只列状态那一半）：

```json
{
  "chain_ref": "req_2026-11-25-a",
  "chain_kind": "wms_requirement_to_analysis",
  "status": "running",
  "current_step": "design",
  "steps": [
    {
      "step_id": "requirement",
      "box_id": "wms_requirement_box",
      "task_type": "capture_business_requirement",
      "status": "completed",
      "task_run_id": "…",
      "wait_for": [],
      "owner": "beeos"
    },
    {
      "step_id": "design",
      "box_id": "wms_design_box",
      "task_type": "handle_design_request",
      "status": "pending",
      "task_run_id": null,
      "wait_for": ["requirement"],
      "owner": "beeos"
    }
  ]
}
```

**编排层的三条纪律**（写进去成本很低，事后补要重排所有盒子）：

1. **别重复同一跳**——编排选下一跳是**确定性规则 + 闭合窗口输入**，
   输入不变就会一直选中同一只盒、反复改同一处。
2. **改过的目标留观察期**——刚落过笔的那一跳，短时间内不重复选中。
3. **全都排除时必须有退路**——宁可重复一次，也不要这一轮什么都不做。

**为什么这三条现在就要写进计划对象**：它们是**计划对象的字段**
（`last_written_at`、`repeat_guard`），不是运行时补丁。
字段晚加，历史记录就补不回来了。

**一条已知约束（来自声明本身）**：`handoff_payload()` 规定
「**一个通道只能接一份产出**」——同一个通道出现两条来源时当场报错。
所以**不是所有协作边界都能「投一次、跑一整条链」**：
学习协作边界三科都投 `subject_result`，成长记录盒就得跑三次，一次一科。
**「一次投料 = 一条链」是假设，不是保证**——编排层要能表达「这一链分几次跑」。

**推进按「数据就绪」，不按「环序」**：拓扑序只是**展示**用的（画环）。
WMS 有三条捷径边（需求→测试、设计→测试、开发→运维），
所以**合法顺序不唯一**——推导出的那个环序恰好等于脚本顺序，
但那是输入顺序的产物，**不是声明保证的**。

执行语义应该是数据驱动的：

> **某只盒子的每条入边通道都拿到了上游产出 → 它就绪了 → 可以跑。**

- 就绪判定 = 查声明里的入边（`handoff_channels`）× 查链状态里的上游产出；
- 缺一份就**不投**（投了也会被契约闸拒——`handoff_payload()` 会跳过没有来源的通道，
  产出的投料缺字段，第一道闸就拦下）；
- 这套语义**天然处理「分多次跑」**：某一跳的输入没齐，它就还没就绪，
  编排层等着，而不是硬排一个顺序往前冲。

### D6 Agent 执行者协议：独立设计项，不进关键路径

**问题**：想「让外部 agent 充当 BeeOS 的模型后端」——
把 `runtime/llm.py` 的 provider 抽象开成通用执行者接口。

**为什么这不是一个小改动**：现在的 provider 是**模型 HTTP 端点**
（`_resolve_endpoint()` 返回 `{base}/chat/completions`，
`_provider_options()` 写死 `provider.minimax`）。
而 agent 可能包含工具、会话、权限和长时间执行——**那不是 HTTP 补全，是一个执行者协议**。

**决策**：**单独立项**，不进本链路的关键路径。三条硬要求先写下来：

| # | 要求 | 说明 |
| --- | --- | --- |
| 1 | **防调用闭环** | agent 等 BeeOS 返回，BeeOS 又等同一个 agent 回答 → 环。协议必须定死「BeeOS 不得同步等待正在等 BeeOS 的执行者」 |
| 2 | **不承诺消除重复推理** | 换成 agent provider 不等于「两边的推理合并了」 |
| 3 | **只给判定辅助，不给判据** | 否则 BeeOS 的验收结论由 agent 决定，「判据留在 BeeOS」就破了 |

**第 3 条最要紧**：agent provider 一旦被用来做**验收判定**，
整个模型的「验收规则留在 BeeOS」这条就名存实亡。

## 4. 对外契约草案

### 4.1 公共契约原则

1. **一份实现，多个适配器**——CLI / HTTP / MCP 共用同一个任务服务层，
   不许任何一个适配器自己抄一份调用逻辑。
2. **契约版本化**——对外发布的形状要有版本号；变更走新增版本，不原地改。
3. **发现面复用现有资产**——`box_manifest()` 已经是为「独立 API 调用者」设计的，
   在它上面加版本化即可，**不推倒重做**。
4. **稳定形状**——对外响应要有稳定字段名与稳定嵌套；
   盒子的产出形状由盒子的 `result_schema` 决定，**适配器不许知道具体某只盒子的产出字段**。

### 4.2 任务服务接口

**这一层是新的**（现有 `kanban/web.py` 的接口是给前端画页面用的，形状不稳定）。

| 动作 | 语义 |
| --- | --- |
| `list_boxes` | 有哪些盒、每只盒能接什么任务 |
| `box_manifest` | 一只盒的完整自描述（输入 / 产出 / 判据 / 例外） |
| `check_intake` | **只过契约闸，不执行**——投料前先验形状 |
| `submit_task` | 提交一次履约，返回 `task_run_id` + `status=queued` |
| `get_run` | 查一次履约的状态、产出、验收结论、执行轨迹 |
| `submit_decision` | 回答一次升级（身份由认证确定，见 D3） |
| `get_chain` | 看链历史（只读） |
| `advance_chain` | 驱动链前进（编排层职责，见 D5） |

**`check_intake` 单独暴露是有意的**：它让 agent 在**不产生履约**的前提下
知道自己投错了没有。投料被第一道闸拦下时不该留下 TaskRun——
今天的 `trigger_task` 已经是这个语义（闸在履约之前）。

**`advance_chain` 不另写链定义**：它从协作边界声明投影出结构
（`core/wiring.py` 的推导 + `Edge.to_task` / `Edge.via`），
再叠加执行状态。**手写的那份链**（`scripts/run_chain.py` 的六跳）
最终要被投影替换掉——两者顺序今天一致，正是替换的前提。

### 4.3 幂等键语义

| 情形 | 行为 |
| --- | --- |
| 同键 + 同载荷 + 无在途履约 | 接受，返回新的 `task_run_id` |
| 同键 + 同载荷 + 有在途履约 | **返回同一个 `task_run_id`**，不新建 |
| 同键 + 不同载荷 / 不同目标 / 不同契约版本 | **拒绝**，并说明冲突在哪一项 |
| 同键 + 上一次已终态 | 返回那一次的记录（不重跑） |

**载荷摘要怎么算**：把「影响这次履约结果的字段」做摘要——
**不含**调用方身份、时间戳这类每次都不同的字段。
否则同一份业务输入换个时间戳就变成「不同载荷」，幂等永远不命中。

### 4.4 只读闭环靠机制，不靠挑盒子

第一版要能**跑完整条链但不落笔**。但今天的盒子**本身就有写副作用**——
开发盒真改代码，实验盒真调 `productUpdate`。

所以「只读」不能靠「这次挑只读盒子」实现，得靠机制：

- 有副作用的 op 在**干跑模式**下不落笔（店铺那条链已经有
  `apply` + 写权限环境变量两道闸，可以直接复用这个思路）；
- 干跑产出的计划要**留痕**，让人知道「这一轮本该改哪里」。

**这样第一版就有价值了**：能验证编排、接力、判据、升级全链路，
又不碰目标对象。

## 5. 分期

| 阶段 | 内容 | 完成条件 |
| --- | --- | --- |
| **1** | **统一任务服务 + 公共契约版本化**：把投料 / 过闸 / 查履约 / 回答升级收进一层；CLI / HTTP / MCP 共用；在 `box_manifest()` 基础上定版本化对外契约 | 不存在第二份调用实现；契约带版本号 |
| **2** | **本地只读 CLI 闭环**：干跑模式跑完整条链，不落笔；执行计划对象落地（结构用声明投影、状态新建，含 D5 的三条纪律字段）；**手写链被投影替换** | 一条链能从头跑到尾且目标对象零改动；重复执行不再选中同一跳；投影结果与手写链逐跳一致 |
| **3** | **身份 + 对象授权 + 幂等 + 持久化执行**：认证接入；`decided_by` 改由认证身份确定；幂等键四件事；`queued` / `running` 语义 | 并发同键只建一次履约；同键不同载荷被拒；伪造 `decided_by` 不再生效 |
| **4** | **受控写入闭环**：写只发生在盒内 op 内；凭证不发给 agent；外部写成功而服务中断时可核对目标状态 | agent 侧拿不到写凭证；中断后可核对，不盲目重做 |
| **5** | **按客户端能力加适配器**：CLI（Codex / Claude Code）→ HTTP / MCP（豆包 / 千问办公 等） | 适配器不新增业务语义；同一契约换适配器不改调用方 |
| **独立项** | **Agent 执行者协议**（D6） | 协议定稿后单独立项；不进上面这条链 |

**顺序理由**：阶段 3 在阶段 4 之前，因为**授权必须在任何对外写能力之前**；
阶段 5 在阶段 3 之后，因为适配器只是同一契约的另一种投法，
而对外暴露之前必须先有身份与幂等。

**每期的验收都要有反例**：并发重复提交、伪造身份、中断后重做、
编排选中刚写过的那一跳——这四个反例各要有一条测试。

## 6. 不做的事 / 已知边界

| 不做 | 为什么 |
| --- | --- |
| 不新增 `queued` 状态 | 现有 `triggered` 就是这个语义 |
| 不为每种 agent 写一套适配逻辑 | 适配器只换投料方式，不换语义 |
| 不把判据交给外部 agent | 判据是 beeBox 的契约，agent 参与定判据 = 验收退化成自评 |
| 不让编排层知道判据内容 | 见 §1.4 边界判据 |
| 不在本稿承诺生产 SLA | 仓库仍是 `0.1.0`，看板无认证、任务同步执行 |

**已知边界**：

- 本文只定**接入面**。盒子内部的形状、判据、beeline 一概不动。
- `apply` 干跑闸目前只覆盖店铺那条链；推广到别的盒子是阶段 2 的工作量。
- 幂等台账是**跨履约**的新机制，与已有的 op 级重试策略不是一回事，两者要分开表述。
- **链序不唯一**：拓扑序只是展示用的，执行靠数据就绪判定；
  想固定执行顺序，得在声明里加显式信号——**现在没有**。
- **一次投料 ≠ 一条链**：有些协作边界一条链要分多次投（见 D5）。

## 7. 术语

| 词 | 这里的含义 |
| --- | --- |
| **外部 agent** | Codex / Claude Code / 千问办公 / WorkBuddy / 豆包 等通用智能体 |
| **任务服务** | 投料、过闸、查履约、回答升级的那一层（新的） |
| **适配器** | 把某种客户端的调用翻译成任务服务调用的一层（CLI / HTTP / MCP） |
| **执行计划** | 一条链的**步骤、状态、等待条件与推进责任**（结构来自声明投影，状态是新建的） |
| **幂等键** | 客户端生成的、标识「这一次投料」的键 |
| **干跑** | 跑完整条链但有副作用的 op 不落笔 |
| **投料** | 向某只盒子的某个任务提交输入 |
| **履约** | 一次完整的执行 + 验收 + 留痕 |
