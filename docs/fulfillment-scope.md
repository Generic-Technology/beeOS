## 0. 一句话

把「盒子之间怎么连」这份事实，从**每只盒子各写一遍**搬到**每个协作边界写一遍**。

盒子不再声明自己接谁、交谁、属于哪个协作边界；协作边界声明成为盒子之间关系的**唯一事实源**；
场图（接线视图）退化为**派生层**——算法住 `core/`，事实归协作边界声明。

### 0.2 落地边界（2026-11-05 定）

> **协作边界声明完整描述关系，装配器验证声明，编排层引用关系，运行记录证明实际发生。**

这四层**各管各的，不互相顶替**：

| 层 | 产物 | 它**证明**什么 | 它**不**证明什么 |
|---|---|---|---|
| **协作边界声明** | `fulfillment_scopes/<边界>/` | **业务上**这些盒子怎么连 | 不证明连得上 |
| **装配器** | `AssembledFulfillmentScope` + `report` | 声明**自洽**（通道明确、端点存在、规则读数）| 不证明**产物**合规 |
| **编排层** | `scripts/run_chain.py` | 按边界里的边**发起**交接 | 不证明交接**成功** |
| **运行记录** | `task_run` / `subject_ref` / `handoff` | **实际发生了什么** | 不证明当时接线长什么样（→ 待定第 16 条） |

**这条边界是本稿最重要的一条**，因为它把三件一直混在一起的事拆开了：

1. **声明层 ≠ 事实层**。`all_archived=5/5` 只说明**归档归属声明完整**，
   **不说明产物进了档案**（真归档在 `runtime/store.py`，§1.7）。
2. **静态判定 ≠ 运行时判定**。`check_schema_compatibility` 判**声明之间**的兼容，
   `validate_payload` 判**产物**能不能进下游——**两个不同的操作**（§5.6）。
3. **合法性 ≠ 展示性**。汇点唯一是**画图**的要求，不是**声明合法**的要求（§5.7）。

### 1.3 边界级意图被复制了 5 份，而它的**例外**没有家

「五个生命周期盒的产物都沉淀进系统档案」是一条**边界级意图**，现在它被写成
**5 份盒子级声明**（design / development / testing / ops / analysis 各写一遍 `feeds_into`）。

**而需求盒不在其中。**

> 这看起来像「复制漏了 1 份」——**不是**。需求盒的 `definition.py` 里写着理由：
>
> > 「需求盒产出的是系统档案的**输入**（读基线：这份系统该是什么样），
> > 不是往档案里加东西。声明它「投给」系统盒，等于说档案是需求盒的下游，
> > 而真实关系正好相反。」
>
> **它是主动不写那条边的。**

**但这条「主动不写」没有任何机制守着。** 它住在**散文**里（盒子文件头的注释），
不是声明。后果：

> 如果有人**善意地**给需求盒补上 `feeds_into=[..., "wms_system_box"]`，
> 协作边界图**照样正常渲染**（汇点还是唯一，环序不变），
> 只是 requirement 成了 `feeds_center` 的一员——
> 而「五个生命周期盒都往系统盒汇」这句话，在数据上不再成立了。
> **没有任何东西会报错。**

需求盒自己的注释已经点破了这件事：

> 「它让 requirement 也成了 feeds_center 的一员，于是
> 『五个生命周期盒都往系统盒汇』这句话在数据上不再成立，
> 而拓扑图是照着这句话画的。」

**这就是「边界级意图复制成 N 份」的真正代价**：不是漏写了一份，
而是**这条规则的边界靠「没人补那条边」维持着**。
加一只新的生命周期盒时，它会不会被归档、协作边界图还是不是原来那张图，
**全靠人记得**。

> 协作边界声明要解决的就是这件事：**让规则的例外有名有姓**（§5.2）。

### 1.6 声明的接线 ≠ 真实依赖图（差 3 条）

`scripts/run_chain.py` 实跑的链路里，**真实的数据交接有 8 条**，
而 `placement.feeds_into` 只声明了 5 条：

| 真实交接（`run_chain.py` 实跑）| 目标字段 | 在 `feeds_into` 里？|
|---|---|---|
| 需求 → 设计 | `requirement_set_ref` | 是 |
| 设计 → 开发 | `design_package_ref` | 是 |
| 开发 → 测试 | `artifact_ref` | 是 |
| **需求 → 测试** | `requirement_ref` | **★否★** |
| **设计 → 测试** | `expectation_ref` | **★否★** |
| 测试 → 运维 | `verification_ref` | 是 |
| **开发 → 运维** | `artifact_ref` | **★否★** |
| 运维 → 分析 | `observation_ref` | 是 |

> **这三条关系现在藏在脚本里。**
> 如果协作边界声明只是「照搬 `feeds_into`」（迁移方案第 2 步的原话），
> 这三条会**继续藏在脚本里**——而协作边界声明号称是「盒子之间关系的唯一事实源」。
>
> **协作边界声明必须记完整的数据依赖图**，编排层（`run_chain.py`）引用边界里的边，
> 不再自己填「来源 + 目标字段」。

### 1.7 归档的真正机制在别处，`feeds_into` 只是拓扑

| | 机制 | 住哪 |
|---|---|---|
| **真归档** | 按 `subject_ref` 分组进工作单元，**只有验过的才进档案**（`accepted_only=True`）| `runtime/store.py` |
| **假归档** | 5 只盒子 `feeds_into=system_box` | 盒子的 `placement` —— **运行时零作用** |

`wms_system_box` 的投料是 `schema_system_probe_input`
（`target_base_url` / `timeout_seconds` / `readonly_endpoints`），**`ref:` 通道数 = 0**——
**它收不到任何上游产出**。

> **所以「五只盒子都投给档案盒」这句话，在运行时是空的。**
> 它真正的意思是：**这五只盒子的产物进 WMS 的系统档案**——
> 而这件事**由 `subject_ref` 机制负责**（五只盒子都声明了
> `subject_ref_field` + `subject_kind="requirement"`），**跟 `feeds_into` 无关**。
>
> **推论**：那 5 条边是**纯拓扑边**（它们的作用是让场图有个中心），
> 不是业务承诺。给它们起个 `kind=archive` 的名字，
> **等于给一条拓扑边赋予了一个它没有的业务语义**——§5.3 的 `all_archived`
> 因此只能读作「**归档归属声明完整**」，读**不能**读作「产物已归档」。

### 1.4 协作边界在仓里没有「家」

- `placement.domain` 只是个**字符串标签**，用来筛盒子、画场图
- `boxes/` 下只有盒子，**没有任何协作边界级目录**
- 边界级业务规则（「本边界的汇点必须是系统档案盒」）**无处可写**
- `core/` 里 `domain` 只是一个字段名

### 1.5 `domain` 一词在仓里指两个东西

| 出处 | 含义 |
|---|---|
| `placement.domain = "WMS"` | **组织分组标签**（筛选 / 场图用） |
| `boxes/wms_design/domain.py` | **DDD 领域本体**（WMS 有 SKU / 货主 / 库位 / 库存 / 批次 / 波次 / 盘点这套概念） |

同一个词「WMS」，一个是「你属于 WMS 这个组」，一个是「WMS 这个领域长什么样」。
`core/models.py` 把两者揉进一句：「domain 答『属于哪个业务领域』」。

## 2. 核心判断

### 2.1 「盒子属于哪个协作边界」和「盒子交给谁」是同一件事的两半

它们都是**盒子在边界里的位置**。拆开放，就是两份事实。

所以：**一起搬进协作边界声明。盒子身上不再留任何协作边界信息。**

推论：`placement.domain` / `placement.feeds_into` / `placement.feedback_into`
**三个字段全部退休**。

### 2.2 「一只盒子属于多个协作边界」这把钥匙

盒子归属若留在盒子上，为了支持多边界，`domain` 得变成 `list[str]`——
那还是「盒子身上的协作边界信息」，割裂没消除，只是换了形态。

**只有把盒子搬进协作边界声明，多边界才天然成立**：盒子出现在 N 个协作边界的 `boxes` 里，
就属于这 N 个协作边界。

> 这条需求反过来否定了「盒子留在盒子上」。

### 2.3 边是业务内容，算法不是

「谁交给谁」是**关于这个领协作边界的断言**，不是关于这只盒子的断言。

盒子能说「我是 WMS 需求捕获盒，我产出需求集包」——那是**它自己的**业务；
但「它交给设计盒」是 **WMS 这个领域**的业务。

所以：

| | 住哪 | 为什么 |
|---|---|---|
| **边**（`Edge`）| **`fulfillment_scopes/<边界>/`** | 含业务断言（「开发盒」「系统档案盒」是业务词）|
| **接线算法**（`derive_wiring`）| **`core/`** | 零业务词；12 个协作边界共用一份，放业务侧就是 12 份拷贝，必然漂 |

**这正是「域」这个实体存在的意义**——它让「领域怎么流转」这个断言有了归属。

### 2.4 场图（接线视图）是派生层，不是事实源

`BeeBoxMap` 的 12 个字段**全部**从各盒子的 `placement` 派生，
**没有一个字段只属于它自己**。

所以它**不需要被管理**（没有需要协调的变更），也**不需要脚手架**（没有声明可装配）。

它只是**照片**。照片不拥有事实。

> 改完之后，`WiringView` 里的**边本身也不在里面**——边在协作边界声明里。
> 它输出的是**拓扑结构**：汇点是谁、环序怎么排、形状是环还是放射。

### 2.5 runtime 不执行协作边界声明

runtime 执行的是**一次履约**：一只盒子自己的 beeline + handler 表。

- 协作边界描述的是**盒子之间**的关系，那是**两次履约之间**的事
- runtime 不认识注册表（见 `runtime/` 的 import 清单：只依赖 `core.beeline_models` /
  `core.conditions` / `core.models`）
- 协作边界的形状（ring / star）对 runtime 无意义——一次履约只跑一只盒子

**依赖方向允许 ≠ 必须使用。** `core/wiring.py` 现在就在 core 里，runtime 一样不碰它。

## 3. 协议

### 3.1 协作边界声明（core，形状）

```python
# core/<domain>.py（新建）
class EdgeKind(str, Enum):
    handoff = "handoff"   # 数据交接：产出交出去给下游验
    archive = "archive"   # 归档归属：这一环的产物进档案（不走通道）
    feedback = "feedback" # 闭环反馈：上一轮结论回到起点变成新一轮输入

class Edge(BaseModel):
    from_box: str
    to_box: str
    kind: EdgeKind
    # **目标 task**：下游有多个 task 时，指明接的是哪一个入口。
    # 单 task 的盒子**可以省略**（唯一推断）——但协议里必须有这个位置，
    # 否则多 task 盒子来了，这条边就指不到具体入口。
    to_task: Optional[str] = None
    # **通道**：仅 handoff 有意义——下游投料里的哪个 `ref:` 字段。
    # 与 `no_channel` **互斥**（D12：反馈边可能本来就没通道）。
    via: Optional[str] = None
    no_channel: bool = False        # 显式声明「这条边没有数据通道」
    external: bool = False          # from_box 在本边界之外（跨边界入口边）

    # **去重按完整通道标识，不按 (from, to, kind)**：
    # 同一个来源可以填下游的**两个不同字段**（两个通道）——
    # 那在 (from, to, kind) 上是同一条边，在通道上是两条。
    # 判重键 = (from_box, to_box, to_task, via, kind)

class RuleKind(str, Enum):
    # **下面三条都是「完备性规则」**：它们约束的是
    # 「**应该被声明、但可能还没被声明**的东西」。
    # 计数期望（盒子数 == N）**不做**——它数的是规则自己，永远绿（§5.3）。
    all_archived = "all_archived"                 # 每只盒子都有 archive 边指向汇点（除豁免）
    all_handoff = "all_handoff"                   # 环上每只非汇点盒子都接到下一环
    each_handoff_has_channel = "each_handoff_has_channel"  # 每条 handoff 边都有通道

class RuleExemption(BaseModel):
    """一条规则的豁免/禁止**——**要能表达「禁止」，不只「允许不做」**"""
    box_id: str
    # **为什么**——结构化，不放注释里。
    # 散文版现在住在需求盒文件头的注释里（§5.3）。
    reason: str
    # **禁止 vs 允许**：
    # - "may"  —— 这只盒子**可以**不参与这条规则（允许豁免）
    # - "must" —— 这只盒子**不得**参与这条规则（业务上禁止）
    # 「需求盒不得归档」是 **must**；把它写成 may，
    # 就拦不住有人给它补一条归档边（§5.3 / §13 第 14 条）。
    mode: Literal["may", "must"] = "may"

class Rule(BaseModel):
    kind: RuleKind
    exemptions: list[RuleExemption] = []

class FulfillmentScopeDeclaration(BaseModel):
    id: str                          # "wms"
    display_name: str
    boxes: list[str]               # 本边界有哪些盒子（唯一一份盒子表）
    edges: list[Edge]                # 盒子之间怎么连（**业务事实**）
    rules: list[Rule] = []           # 边界级完备性规则（**业务断言**，判据是机制）
    # 注：规则的**豁免要带 box_id + reason + mode**——
    # 只有 box_id 的豁免表达不了「不得归档」（§13 第 14 条）

class AssembledFulfillmentScope(BaseModel):
    """装好的协作边界——与 ``AssembledBox`` 对称"""
    declaration: FulfillmentScopeDeclaration   # 装好的协作边界声明
    wiring: WiringView               # 拓扑投影（派生，见 core/<wiring>.py）
    rules_reading: list[Any] = []    # 边界级规则读数（第二阶段才有）
    report: AssemblyReport           # 装配期结论：装好了没、有什么问题
```

**core 只定形状，不含业务词。** 具体值（`"wms_system"`、`"via=design_package_ref"`）
在 `fulfillment_scopes/<边界>/` 侧填。

**边是业务内容，算法不是** —— 这是本方案最容易含糊的一处：

| | 是什么 | 含业务断言吗 | 住哪 |
|---|---|---|---|
| **边**（`Edge`）| 「WMS 边界里设计盒交给开发盒」| **含** ——「开发盒」「系统档案盒」是业务词 | **`fulfillment_scopes/<边界>/`** |
| **接线算法**（`derive_wiring`）| 「有 N 个汇点时画不出图」「环上相邻必须有交接边」| 不含 —— 零业务词 | **`core/`** |

为什么边是业务内容：**「谁交给谁」是关于这个领协作边界的断言，不是关于这只盒子的断言。**
盒子能说「我是 WMS 需求捕获盒，我产出需求集包」——那是**它自己的**业务；
但「它交给设计盒」是 **WMS 这个领域**的业务：需求捕获与设计之间那条交接，是领域定的。

> 这正是「域」这个实体存在的意义——它让「领域怎么流转」这个断言有了归属。

而接线算法必须留 core，理由与 `core/models.py` 的 `SchemaDef` 形状 +
`runtime/contract.py` 的校验算法完全同构：

```
boxes/wms_design/schemas.py   ← schema_business_design_package（业务事实）
core/models.py                ← SchemaDef（形状）
runtime/contract.py           ← 校验算法（机制）

fulfillment_scopes/<边界>/<scope>.py      ← Edge(...) / FulfillmentScopeDeclaration（业务事实）
core/<domain>.py                ← FulfillmentScopeDeclaration 的形状 + assemble_domain（机制）
core/<wiring>.py              ← 接线算法（机制）
```

**若接线算法住 `fulfillment_scopes/`**，12 个协作边界就要 12 份拷贝——必然漂。
现在它在 `core/wiring.py` 已经是这个位置，改名只是让它更准。

### 3.2 协作边界声明（业务侧，一份样例）

```python
# fulfillment_scopes/<wms>/<scope>.py（新建）
DOMAIN = FulfillmentScopeDeclaration(
    id="wms",
    display_name="WMS 仓储",
    boxes=[
        "wms_requirement", "wms_design", "wms_development",
        "wms_testing", "wms_ops", "wms_analysis", "wms_system",
    ],
    edges=[
        Edge(from_box="wms_requirement", to_box="wms_design",
             kind=EdgeKind.handoff, via="requirement_set_ref"),
        Edge(from_box="wms_design", to_box="wms_development",
             kind=EdgeKind.handoff, via="design_package_ref"),
        # 归档归属：不是交接，是「这一环的产物进档案」——不需要 via
        Edge(from_box="wms_design", to_box="wms_system", kind=EdgeKind.archive),
        # 闭环边：单独一种，进拓扑排序会成环
        Edge(from_box="wms_analysis", to_box="wms_requirement", kind=EdgeKind.feedback),
    ],
)
```

### 3.3 三条边界规则

**① `via` 只说「哪个字段」，不说「什么形状」。**

形状是**下游自己声明的**（`B/schemas.py` 里的 `requirement_set_ref: ref:schema_requirement_set_input`）。
协作边界说「通过哪个字段」，schema 说「那个字段是什么形状」——**各说一半，不重复**。

若协作边界声明里也写上 shape，就与 `B/schemas.py` 变成同一事实两份。

**② 协作边界声明里不列盒子以外的东西。**

盒子 = `boxes`（唯一一份）；边界级规则 = 另加 `rules`（若有）；
**接线 = `edges`**。三者都不许在别处再写一遍。

**③ 一条边出现在协作边界 D 里，当且仅当两端都是 D 的盒子**（`external=True` 的入口边除外）。

一只盒子属于 N 个协作边界，就带着它的边在 N 个边界里各出现一次。
**这不是重复，是两个视角各自正确。**

## 4. 派生层：接线投影怎么改

**`core/field_map.py` 改名 `core/<wiring>.py`，继续存在，但输入变了**：

| | 现在 | 之后 |
|---|---|---|
| 输入 | `Sequence[PlacementView]`（手工抄的视图）| `FulfillmentScopeDeclaration` 的 `boxes` + `edges` |
| 事实源 | 各盒子的 `placement` | **协作边界声明**（`fulfillment_scopes/<边界>/`）|
| 位置 | `core/field_map.py` | `core/<wiring>.py`（仍是 core 的派生层）|
| 输出 | `BeeBoxMap` | `WiringView`（`AssembledFulfillmentScope` 的一个字段）|

**它从「认 placement」改成「认协作边界声明」——仍然不拥有事实。**

**为什么叫 `wiring` 而不是 `field_map`**：它派生的是**接线**，不是「场」。
「场图」是那个**渲染出来的东西**（画布上那张图），不是这个**算法**。

**`WiringView` 里没有边本身**——边在协作边界声明里。它输出的是**拓扑结构**：
汇点是谁、环序怎么排、形状是环还是放射、以及**边按 `kind` 分类后的分布**。

命名对照（避免「Map」既指事实又指视图）：

| 现在 | 之后 |
|---|---|
| `core/field_map.py` | **`core/<wiring>.py`** |
| `derive_field_map()` | `derive_wiring()` |
| `field_map_of_scope()` | `wiring_of_scope()` |
| `BeeBoxMap` | `WiringView` |
| `PlacementView` | `BoxFacts`（盒子归属搬走后，它抄的就是「这只盒子的事实」）|
| 前端 label `... · BeeBox Map` | **不改**（见下）|
| 协作边界声明（新） | **协作边界**（Domain）——唯一的事实源 |

> **⚠️ 前端 label 这一行当初写错了（2026-11-05 实现时发现）**：
> 初版写「`... · BeeBox Map` → `... · 场图`」。
> **但看板早就有一条守卫明写「别再用自造的词『场』当标签」**——
> 理由是：「活儿」「场」这类自造词业务方看不懂，
> 而产品名（BeeBox）本来就在标题里出现过，是**现成的词**。
>
> 那是**先于本文的产品决策**，而且有守卫在守。

>
> **教训**：改名的清单不能照着「新概念更准确」一路推——
> 每一项都得问「**有没有别处已经拍过板的约束**」。
> 名字准不准是次要的，**跟已拍板的东西打架是主要的**。

**改名牵涉的文件**（都已改完）：
`kanban/trigger.py` / `kanban/web.py` / `scripts/new_box.py` /
`tests/test_learning_boxes.py` / `tests/test_docs_match_code.py` /

## 5. 装配期校验（边界级）

与 `core/scaffold.py` 的 C1–C12 同构，边界级校验同样在装配期报错。

**判定机制共用一份**：这些校验应加成 `core/<decl_checks>.py` 里的
`check_domain_*` 系列（那儿已经是「声明自洽判定的唯一真源，装配器与体检台共用一份」），
**不在 `core/<fulfillment_scope>.py` 里另写一套判定**。

| # | 校验 | 不这么做会怎样 |
|---|---|---|
| D1 | 每个 `boxes` 里的盒子都在注册表里存在 | 悬空盒子 → 协作边界的盒子表里有个不存在的盒子 |
| D2 | 每条边的两端都在 `boxes` 里（或声明为 `external`）| 边指向边界外的盒子却没说明 → 拓扑漏边 |
| D3a | `handoff` 边必须有 `via`，且 `via` 必须是下游 `task_schema` 里的 `ref:` 字段 | 声明了交接却没有通道 → **搬的时候没做 `kind` 分类，就会被这条全拦下** |
| D3b | `via` 指向的 `ref:` schema 能在**下游自己的** schemas 里解析 | 通道指向一个不存在的形状 → 交接时才发现 |
| D3c | **上游声明的产出形状，能满足 `via` 指向的那份接料形状**（静态兼容判定，见 §5.6）| 通道名对、形状对不上 → 交接时才发现，错误离现场隔着两层 |
| D4 | `feedback` 边不进拓扑排序 | 闭环边混进主干 → 排序遇环 → **静默按原顺序收尾** |
| D5 | ~~汇点唯一~~ → **移到「展示适用性」**（见 §5.7）| 汇点唯一是**画图**的要求，不是**合法性**的要求 |
| D6 | 主干无环 | 环上顺序变成任意的，图照常渲染，结构是错的 |
| D7 | 每条边两端的 `kind` 合法（`archive` 不得有 `via`）| 归档归属被当成数据交接 |
| D8 | 判重键 = `(from_box, to_box, to_task, via, kind)`，**不是 `(from, to, kind)`** | 同一来源填下游两个不同字段 → 两条合法通道被当成重复 |
| D9 | 每只已注册盒子要么属于至少一个协作边界，要么显式声明 `standalone` | 忘了归协作边界 → 盒子不在任何协作边界里，却没人知道 |
| D10 | 每条边的两端都属于本边界（`external=True` 除外）| 跨边界边混进本边界 → 拓扑算错 |
| D11 | **每条 `handoff` 边都必须有通道**（D3a/b/c 三级全过）| 声明了交接却走不通 → **现在 11 条声明边里有 6 条没有通道**（5 条投档案盒 + 1 条闭环反馈），搬的时候不做 `kind` 分类就会被这条全拦下 |
| D12 | 每条边**要么有 `via`，要么显式声明 `no_channel`**（两者互斥）| 反馈边到底通不通，现在看不出来 |
| D14 | 每条豁免的 `box_id` 都在协作边界的 `boxes` 里；`reason` 非空；`mode` 合法 | 豁免写了个不存在的盒子 → 豁免静默失效 |
| D15 | `mode="must"` 的豁免：该盒子**不得**存在对应的边 | 「需求盒不得归档」写成「可以豁免」→ **拦不住有人给它补归档边** |

**D11 是这套校验里最有价值的一条**——它把「声明了交接但没有通道」从**静默**变成**装配期就拒**。

**D1–D12 与 C1–C12 的分工**：C* 验「一只盒子自不自洽」（core 不认识注册表，只查自己）；
D* 验「一个协作边界的结构对不对」（需要盒子信息，由调用方从注册表收集后传入）。

### 5.1 D3 为什么必须拆成三级（实测逼出来的）

原以为 D3 一条就够：「`via` 是下游投料里的 `ref:` 字段」。**实测证明不够**，而且差得很远。

实测（`requirement → design` 这条边）：

```
下游 design 声明的通道：requirement_set_ref: ref:schema_requirement_set_input
上游 requirement 的产出：schema_requirement_set_package
                         ↑ id 根本不一样
```

而且**形状不是相等，是包含**（实测，2026-11-05）：

| | 上游产出 `schema_requirement_set_package` | 下游声明 `schema_requirement_set_input` |
|---|---|---|
| 字段总数 | **14** | **5** |
| 必填 | **12** | **2**（`set_id` / `requirements`）|
| 可选 | 2（`context` / `document`）| 3（`business_goal` / `context` / `source_sentences`）|

**下游的 5 个字段，上游全都有**；下游只把其中 3 个从必填放宽成可选，
另外 9 个上游字段（`nodes` / `edges` / `requirement_count` / 4 条判据 / …）**下游根本不要**。

**下游声明的是「它自己要的那一小块」，不是上游的全部。** 这是「形状由消费者声明」的真正含义：
消费者**不是复制上游的 schema**，而是声明「我接你的哪一部分、宽松到什么程度」。

**所以 D3c 不能做「id 相等」，也不能做「形状相等」**：

> D3c 判的是**声明层**的包含关系（下游接料形状 ⊆ 上游产出形状），
> **不是**拿一份样例去试（那样只能证明「**存在**一个合规产出能过」，§5.6）。
> 具体怎么做、为什么不能拿样例试、什么情况下只能给 `unknown` —— 见 **§5.6**。

这跟仓里已经踩过的坑是同一条纪律（`core/conditions.py` 的 docstring）：

> 「它是协议，不是执行……两处各写一份 = 两份事实 = 漂。」

**所以「形状兼容判定」不能另写一套——它必须和运行时校验**共享同一份类型规则**。**

> **⚠️ 但 2026-11-05 修正（§5.6）**：这两件事**不是同一个操作**：
> - **`validate_payload`**（产物层）：真产物 vs 接料形状 —— 运行时用
> - **`check_schema_compatibility`**（声明层）：两份**声明**之间的包含关系 —— 装配期用
>
> 它们**共享类型规则**（同一套「什么类型算兼容」的定义），
> 但**不能相互替代**：拿样例试只能证明「存在一个能过」，不能证明「全都能过」。
>
> → 所以待定第 6 条要改口径：**不是把 `validate_payload` 整个下沉，
> 而是下沉「类型兼容规则」那一份**，让两个操作共用它。

**→ 倾向：把类型兼容规则下沉到 `core/<contract>.py`，
`runtime/contract.py` 从 core import。**

依据同 `core/conditions.py`：**它是协议，不是执行**。
现在它住在 `runtime/` 只因为 runtime 是第一个用它的人；协作边界装配期也要用它，且必须是同一份。
（影响面：`runtime/contract.py` + `runtime/handoff.py` + `kanban/trigger.py` +
`boxes/wms_requirement/runner.py` + 约 12 处测试引用——**下沉要连带把测试的 import 一起改**。）

### 5.2 协作边界能机械测的量（WMS 实测清单，2026-11-05）

待定项「边界级规则第一版要不要有」的前置问题是「**协作边界能测什么**」。
下表是**实测出来的**答案——每一行都是能机械判定、且**不需要 core 认识任何业务词**的量：

| # | 量 | WMS 实测值 | 怎么测 | 能不能失败 |
|---|---|---|---|---|
| M1 | 协作边界盒子数 | **7** | `boxes` 长度 | ❌ 自证（见下）|
| M2 | 汇点数 | **1**（`wms_system_box`）| 出度 0 且入度 > 0 | ✅ 能（多汇点 / 无汇点）|
| M3 | 接线形状 | **ring** | 边界内有交接边 → 环；无交接边 → 放射 | ✅ 能 |
| M4 | 环序 | requirement→design→development→testing→ops→analysis | 交接边拓扑序 | ✅ 能（成环）|
| M5 | 环上相邻必有交接边 | **成立** | 逐对查边 | ✅ 能 |
| M6 | 边界内交接边数 | **5** | `kind=handoff` | ❌ 自证 |
| M7 | **交接边有通道数** | **5 / 5** | D3a/b/c 实跑 | ✅ 能 |
| M8 | 投汇点边数（`archive`）| **5** | `kind=archive` | ❌ 自证 |

| M13 | 跨边界边（端点不在本边界）| **0** | 边端点 vs `boxes` | ✅ 能 |

> 而今天没有任何东西在看它们。

### 5.3 边界级规则第一版：**完备性规则**，不是计数期望

**关键区分：一条规则能不能失败，取决于它约束的是「已经声明的东西」还是「应该被声明却没被声明的东西」。**

| 规则形态 | 例 | 能抓到什么 |
|---|---|---|
| **计数期望** | 「本边界盒子数 == 7」| **弱**：只能抓「改了盒子清单、忘了改期望值」这一种漂移 |
| **完备性规则** | 「除豁免外，每只盒子都要有一条 `archive` 边指向汇点」| **强**：抓「**该声明的边根本没写**」——新加一只盒子忘了归档，它就抓得到 |

> **⚠️ 修正（2026-11-05）**：初版写「计数期望**永远绿** = 没有检查」——
> **这是错的**。规则里的 `7` 是**独立写的字面量**，比较的是
> `len(boxes)` 与那个字面量，**改了清单忘了改规则就会红**。
> 仓里已有同族先例：`test_box_readme_scale_numbers_match_definition`
> 就是拿声明的数字去对实际。
>
> **所以正确的说法是「计数期望弱、完备性规则强」，不是「计数期望无效」。**
> 优先完备性，是因为它抓的是**另一类错**（漏声明），不是因为计数期望抓不到东西。

**第一版只做三种完备性规则，全部只引用协作边界声明 + 注册表：**

| kind | 判据 | WMS 应读数 | 现在会抓出谁 |
|---|---|---|---|
| `all_archived` | 除豁免外，每只**非汇点**盒子都有 `archive` 边指向汇点 | 6 只非汇点盒子 − **豁免 1** = 该归档 **5** 只，实际 **5** 只 → **5/5 通过** | **新增的盒子忘了归档** |

> **⚠️ 这个读数只能读作「归档归属声明完整」，读**不能**读作「产物已归档」**（2026-11-05）。
>
> 因为那 5 条 `archive` 边**运行时零作用**：
> `wms_system_box` 收不到上游产出（投料 0 个 `ref:` 通道），
> 真正的归档在 `runtime/store.py`（按 `subject_ref` 分组 + `accepted_only`）——**§1.7**。
>
> **换一种边类型，并没有补上归档动作。**
> 「声明层」与「事实层」必须分开展示：**规则读数是声明层，
> 「产物真的进了档案」是事实层，只能由运行记录证明。**
| `all_handoff` | 每只**非汇点**盒子都在交接链上（本边界至少有一条 `handoff` 边，**入边或出边**）| WMS **6 / 6**、Learning **3 / 3** | **新增的盒子忘了接进链** |
| `each_handoff_has_channel` | 每条 `handoff` 边都有通道（D3a/b/c）| WMS **8 / 8**、Learning **3 / 3** | **声明了交接却走不通** |

> **⚠️ `all_handoff` 的判据在实现时改过（2026-11-05）**：
> 初版写的是「**环序上**每只非汇点盒子都有 `handoff` 边接到下一环」。
> 那是**按环写的**——可交接图**不一定是一条链**：
> 真实的数据依赖图里有「抄近路」的那 3 条（需求→测试、设计→测试、开发→运维）。
> 按环写会把它们判成「没接到下一环」。
>
> 改成「**在本边界至少有一条交接边**（入边或出边）」：
> - 仍能抓住「新加的盒子一条边都没有」（它不在任何交接边上）；
> - 不挑链的**末端**（分析盒没有交接出边，它的出边是归档和闭环反馈——
>   **要求出边会把合法结构判成错**）；
> - **放射形状的协作边界也适用**（三科各自直投成长记录，三只都在交接边上）——
>   这跟 §5.5 的结论一致：**规则要挂在 `kind` 上，不要挂在「环/汇点」上**。

**为什么规则里必须带「豁免」**：需求盒就是豁免——它**有意**不归档（§1.3）。
而豁免的理由现在住在**需求盒文件头的注释里**（散文）。
协作边界声明给了它一个正经的家：

```python
# fulfillment_scopes/<wms>/<scope>.py
rules=[
    Rule(
        kind="all_archived",
        exemptions=[
            RuleExemption(
                box_id="wms_requirement",
                # 本边界的过程产物都沉淀进系统档案。
                # 需求盒是**不得**归档的：它产出的是系统档案的**输入**
                # （读基线：这份系统该是什么样），不是往档案里加东西——
                # 声明它「投给」档案盒，等于说档案是需求盒的下游，
                # 而真实关系正好相反。
                reason="它产出的是档案的输入（读基线），不是往档案里加东西",
                # **must，不是 may**：业务要求是「**不得**归档」，
                # 写成 may 拦不住有人给它补一条归档边（D15）。
                mode="must",
            ),
        ],
    ),
]
```

**「为什么需求盒不归档」这句话，从此住在边界级声明里，而不是某只盒子的注释里。**
而且它是**结构化的**（`box_id` + `reason` + `mode`），不是散文——
体检台（`workshop/`）才能把它显示出来。

**规则的表达原则**（与 §3.3 同源）：

> **边界级规则只能引用「协作边界声明里已有的东西」+「注册表」+「盒子的 schema」。**
> 想引用「某只盒子是什么角色」（例如「汇点必须是系统档案盒」），就得先让盒子声明角色——
> 那是**另一件事**（盒子的业务分类），第一版不碰。
> **core 判不了的，就别写进规则。**

### 5.4 边界级规则的可读数（`rules_reading`）

`AssembledFulfillmentScope.rules_reading` 现在有位置了——它是**规则的读数**，不是规则的定义：

```
all_archived              5/5   (6 只非汇点盒子，豁免 1: wms_requirement)
all_handoff               5/5
each_handoff_has_channel  5/5
```

**读数要能在装配期就出来**（不是等第一次履约才知道），
所以装配期就得能**验通道** → 又回到 §5.1 的 D3c → 又回到 §5.6 的
`check_schema_compatibility` → 又回到「**类型兼容规则**下沉 core」（待定第 6 条）。

### 5.5 实测推翻了一条假设：**规则不能只按「环」写**

Learning 协作边界（4 只盒子：math / chinese / english → growth）是**放射**（star），
实测它的三条边（2026-11-05）：

| 边 | 通道 | 判定 |
|---|---|---|
| `learning_math` → `learning_growth` | `subject_result: ref:schema_learning_subject_result` | ✅ 有通道 |
| `learning_chinese` → `learning_growth` | 同上 | ✅ |
| `learning_english` → `learning_growth` | 同上 | ✅ |

**三条边全是真交接（handoff），而且共用同一个通道字段。**
三科的产出是三个不同的 schema（`schema_learning_math_output` / `_chinese_` / `_english_`），
但**字段完全相同**（10 个，名字和类型都一样），
growth 声明的接料形状 `schema_learning_subject_result` 是那 10 个字段的**子集**（9 个）。

**于是 §5.3 那三条规则，Learning 边界里有两条不适用**：

| 规则 | ring 协作边界（WMS） | star 协作边界（Learning） |
|---|---|---|
| `all_archived` | 适用（5/5）| **不适用**——源盒的边是 handoff，不是 archive |
| `all_handoff` | 适用（6/6）| **适用**（3/3）——「源盒有没有交接边」，跟有没有环序无关 |
| `each_handoff_has_channel` | 适用（8/8）| **适用**（3/3）|

> **⚠️ 修正（2026-11-05，实现时）**：初版这里写 `all_handoff` 在 star 协作边界
> **不适用**，理由是「没有环序」。
> 但改后的判据是「**在本边界至少有一条交接边**」（见 §5.3 的修正框），
> 它跟环序**无关**——三科各自直投成长记录，三只都真的有交接边。
> 所以它在 star 协作边界**适用而且通过（3/3）**。
>
> **这正是本节结论的兑现**：规则挂在 `kind`（有没有交接边）上，
> 而不是挂在「环/汇点」这种拓扑位置上。

> **「汇点」这个词盖了两种东西。**
>
> | 协作边界 | 汇点 | 汇点收不收上游产出 |
> |---|---|---|
> | WMS | `wms_system_box`（档案盒）| **不收**——它是去线上读的，所以那 5 条是 `archive` 边、**没有通道** |
> | Learning | `learning_growth_box`（成长记录）| **收**——所以那 3 条是 `handoff` 边、**有通道** |
>
> **「汇点」只是拓扑位置（边界内没有下游的那只），不是角色。**
> 决定一条边是 `handoff` 还是 `archive` 的**不是它指向不指向汇点，而是「数据真的流过去吗」**——
> 这正是 `kind` 存在的理由：**kind 才是事实，汇点只是拓扑。**
>
> **所以规则不能挂在「汇点/非汇点」上，要挂在 `kind` 上。**

### 5.6 D3c 要拆成**两个操作**：静态兼容判定 + 运行时产物校验

> **⚠️ 本节于 2026-11-05 整节重写。** 初版写的是
> 「合成样例能过 ≈ 任何合规产出都能过」——**这句话是错的**。

**反例**（用项目自己的 `runtime.contract.validate_payload` 复现）：

```
上游允许：status ∈ {ready, blocked}
下游允许：status ∈ {ready}

合成样例 ready   ：两边都通过 ✅
合法产出 blocked ：符合上游，过不了下游 ❌
```

**根因**：`synth` 对 `enum` 取的是**第一个**合法值，不是**全部**合法值的**集合**。
「**存在**一个合规产出能过」≠「**所有**合规产出都能过」。

**而这条在真实链路上就存在**（实测 2026-11-05）：

| | 上游 `schema_test_report` | 下游 `schema_ops_verification_input` |
|---|---|---|
| `observations[].outcome` | `string`（**无值集**）| `enum` ['pass','fail','not_applicable','indeterminate'] |

上游**声明**允许任意字符串，下游只收 4 个值 →
**静态判不出**上游会不会产出下游不接的值。

**所以要两个不同的操作**：

| 操作 | 判什么 | 住在哪 | 结果 |
|---|---|---|---|
| **`check_schema_compatibility`** | **声明层**：下游接料形状 ⊆ 上游产出形状？ | `core/`（装配期）| `compatible` / `incompatible` / **`unknown`** |
| **`validate_payload`** | **产物层**：真产物能不能进下游接料形状 | `runtime/`（履约时）| 通过 / 报错 |

**`check_schema_compatibility` 能静态判的**：
- 下游必填的字段，上游产出形状里**存在**且类型兼容
- 下游的 `enum` 值集 **⊆** 上游的 `enum` 值集
- **上游没声明值集 → `unknown`**（**不是** compatible！）

**`unknown` 必须是一等结果**：
「上游声明是 plain string」**推不出**「上游不会产出下游不接的值」。
把它当 compatible，就是**用一个猜测换掉一个证明**。

**还有一个前提要澄清**：初版说「产物必然符合上游 `result_schema`」——
**这也没有通用运行时保证**：runtime 里**没有任何地方**把产物校验到上游自己的
`result_schema`（`runtime/handoff.py:142` 校验的是**下游**声明的接料形状）。
「产物符合上游声明」是**上游自己的责任**，不是 runtime 保证的。

**→ 更根本的修法：把上游的声明改精确。**
`schema_test_report.observations[].outcome` 现在声明成 `string`（实际只产 4 个值）——
**改成 `enum` + values，静态判定立刻成立**。
**上游声明越精确，能静态判的越多；`unknown` 的地盘就越来越小。**

### 5.7 三层分离：**声明合法性 / 边界业务规则 / 展示适用性**

初版把「汇点唯一」写成 D5（合法性校验），理由是「多个汇点 → 圆心算不出来」。
**那是展示层的限制，被写成了合法性要求。**
多终点、分叉、孤立成员**都可能是合法业务结构**。

| 层次 | 判什么 | 例子 | 住在哪 |
|---|---|---|---|
| **① 声明合法性** | 这份声明**本身**对不对 | 盒子存在（D1）、通道明确可解析（D3a/b）、边端点在边界内（D2/D10）、豁免合法（D14/D15）| `core/decl_checks.py`（`check_domain_*`）|
| **② 边界业务规则** | **这个协作边界**自己额外要求的 | 本边界要求唯一归档目标；本边界每只盒子都要归档（`all_archived`）；本边界闭环必须有反馈边 | `fulfillment_scopes/<边界>/` 的 `rules`（业务断言）|
| **③ 展示适用性** | 这份声明**能不能画成环/放射** | 汇点唯一吗？环上相邻有交接边吗？分叉能排成环吗？ | `core/<wiring>.py`（派生层）|

**D5 因此从 ① 移到 ③**：
- **汇点不唯一** → 声明**合法**；只是「画不成环」
- **分叉** → 声明**合法**；只是「环序排出来会有相邻无边的一对」（已有 `not_a_chain`）
- **孤立成员** → 声明**合法**（只要按 §13 第 13 条显式点名）；只是「画不成图」

> **原则：汇点、环、形状，都是从明确语义（`kind`）派生的**——
> **不能反过来决定边的业务含义**（§5.5 已证：`kind` 才是事实，汇点只是拓扑）。

### 6.1 跨边界边：两端不共享任何协作边界

例：「Learning 协作边界的盒子要用票据盒（未归范围）的产出」——这条边**不属于 WMS 也不属于 Learning**。

> **实测修正（2026-11-05）**：**现在没有任何盒子用票据盒的产出。**
> `receipt_capture_box` 没有任何一条 `feeds_into` / `feedback_into` 指向它，
> 也没有任何盒子的投料里有 `ref:schema_receipt_parsed` 通道——
> **它的 20 个字段的产出完全悬空。**
> 所以这只是个**假想的例子**，不是现状的描述。
> 真正的现状是：**它是个孤儿盒子**（产出没人接），见 §6.2。

**解法**：协作边界可以声明**外部边**，挂在**接收方**的边界里：

```python
Edge(from_box="receipt_capture", to_box="wms_requirement",
     kind=EdgeKind.handoff, via="receipt_ref", external=True)
```

这比现在 `scope_field_map` 的「跨边界整体无图，给一句原因」更细：
**不是「跨边界整体无图」，而是「跨边界的那一条边挂在接收方边界里」。**

### 6.2 「未归范围」的盒子（`receipt` 现在就是）

它就是「不出现在任何协作边界的 `boxes` 里」。但要区分**「有意的独立」**和**「忘了加」**。

> **实测（2026-11-05）**：`receipt_capture_box` 未归范围、没人投给它、
> 它的 20 字段产出也没有任何盒子能接。
>
> **⚠️ 初版据此写「所以『有意的独立』这个解释站不住」——那也是错的。**
> 补测发现：**它没有 `subject_ref_field`，也没有 `subject_kind`**
> → 它**根本不进归档分组**（归档只收声明了工作单元的履约）。
>
> **所以「没有下游」推不出「不该独立存在」**：
> 它的产出是**给人直接读的**（票据识别结果——商家、金额、税额、判据），
> 人或外部调用者可以直接消费。**「没有盒子接它」和「没人用它」是两件事。**
>
> **这条的正确读法**：`receipt` 是一只**独立的、产出直接给人读的**盒子，
> 不属于任何协作边界——**而这正是 `standalone` 要表达的东西**（待定第 3 条）。

**解法**：盒子自己声明 `standalone: bool`（这是「我不参与任何协作边界」的**业务属性**，
不是协作边界信息，不违反「盒子不留协作边界信息」）。

### 6.3 盒子清单要手工维护（已定要写，代价已知）

协作边界声明的 `boxes` 是一份需要维护的清单——**加盒子忘了加进协作边界，它就不在边界里**。

这不是「第二份事实」（盒子已经不声明 domain 了），但**必须有守卫兜底**：
**D1**（清单里的盒子在注册表里存在）+ **D9**（每只已注册盒子要么在某个协作边界的清单里，要么 standalone）
+ **「孤岛须显式点名」**（清单里的盒子在本边界至少有一条边；做不到的要显式豁免——
抓「加进协作边界忘了接边」，见 §14）。

**为什么宁可手写，也不要推导**（完整论证见 §12.1）：
「档案盒属于 WMS 协作边界」是**业务判断**，不是接线结果——
它一条 handoff 边都没有，属于 WMS 是因为**它存的是 WMS 的档案**。

**脚手架知道要加哪个协作边界** → `scripts/new_box.py` 可以直接改协作边界声明，不必人去记。

**现在藏在 `scripts/run_chain.py` 里**（§1.6）。照抄 = 那 3 条继续藏着，
而协作边界声明号称是唯一事实源。

**(二) 这 8 条 + 5 条归档边 + 1 条反馈边，**不是**同一种边**：

| 现在 | 条数 | 搬成 | 有通道吗 |
|---|---|---|---|
| requirement→design、design→development、development→testing、testing→ops、ops→analysis | **5** | `kind=handoff`（`via` 写各自的 ref 字段名）| **全部有** |
| **requirement→testing（`requirement_ref`）、design→testing（`expectation_ref`）、development→ops（`artifact_ref`）** | **3** | `kind=handoff` | **全部有**（**`feeds_into` 里根本没有这 3 条**）|
| design→system、development→system、testing→system、ops→system、analysis→system | **5** | `kind=archive`（**不带 `via`**）| **全部没有**——档案盒是去线上读的，不收上游产出 |
| analysis→requirement | **1** | `kind=feedback` | **没有**——这条边是「开新一轮需求」，不是数据交接 |

> **如果第 2 步只是照抄 `feeds_into`**：
> ① 那 6 条没有通道的边会被搬成 `handoff`，被 D3c 全部拒掉；
> ② 那 3 条真实交接会**继续藏在脚本里**。
> 正确做法是**先补齐、再分类**。

**③ 编排层要引用边界里的边。**
`scripts/run_chain.py` 现在自己填「来源 + 目标字段」（第 491–553 行）。
迁完之后，**它应该从协作边界声明里读边**（`via` 就是它要填的那个字段名），
不再自己抄一份。**否则协作边界声明和脚本又是两份事实。**

**第 3 步会抓出来的东西**：那 5 条 `archive` 边搬完之后，
「需求盒没有 archive 边」这件事就会变成**一条显式的豁免**
（§5.3），而不是**一句藏在需求盒注释里的话**。

## 10. 不做什么

- **不把场图做成持久化实体**——它是派生层，没有需要协调的变更；持久化它 = 第二份接线事实
- **不让 runtime 执行协作边界声明**——runtime 只跑单盒，协作边界是两次履约之间的事
- **不在协作边界声明里写「什么形状」**——形状归下游 schema（各说一半，不重复）
- **不手写「协作边界接线表」**——协作边界声明**就是**唯一真源，再写一份就是 `BOX_META` 当年的病
- **不在 `fulfillment_scopes/` 里放场图**——场图是 `core` 的派生产物；`fulfillment_scopes/` 装的是**声明**
- **不扫描目录发现协作边界**——协作边界是显式声明的（与盒子注册表同一条纪律）
- **不把 `domain` 一词继续复用**——分组标签、DDD 领域本体、DDD 构件类型是三个东西
- **不做计数期望型边界级规则**——「盒子数 == 7」永远绿，**自证的检查等于没有检查**（§5.3）
- **不写 core 判不了的规则**——「汇点必须是系统档案盒」需要盒子先声明角色，
  那是另一件事；第一版只做引用完整性（§5.3）
- **不为 `archive` / `feedback` 边硬造通道**——档案盒是去线上读的，不收上游产出；
  给它加一个假的 `ref:` 通道，是**造一根不存在的线**（§7）

### 12.1 关于「协作边界的盒子清单」：**声明，不推导**（已定，2026-11-05）

> **⚠️ 本节论证于 2026-11-05 修正过一次**（初版的理由是错的，见下面的「修正」框）。
> **决定不变，理由换了。**

**问题**：协作边界声明里要不要手写一份「本边界有哪些盒子」的清单（`boxes`），
还是让它是**推导**出来的（由边算连通分量）？

**实测（附录 B3）**：现在的协作边界分组**恰好就是**边的连通分量——

```
WMS 7 只 / Learning 4 只 / receipt 1 只  ←  与连通分量完全一致
```

**而且按 `kind` 分开、把那 5 条 archive 边也算进去，仍然完全一致。**
→ **推导在现状下是可行的——它不会算错。**

> **修正（2026-11-05）**
>
> 本节初版写的是：「『档案盒属于 WMS 协作边界』靠的不是接线，是业务判断——
> **它一条 handoff 边都没有**」。
>
> **这句话不准确。** 档案盒有 **5 条入边**（design / development / testing / ops /
> analysis 各一条）。字面成立的是「一条 **handoff** 边都没有」——
> 那 5 条全是归档边。但「靠的不是接线」是**错的**：它明明有接线，
> 而且**用边推成员在现状下压根不会算错**（实测完全一致）。
>
> **所以「成员必须声明」的真实理由跟「档案盒有没有边」无关，是下面两条：**

**理由一：多边界**（§2.2 的目标能力）

连通分量是**全局唯一划分**——一只盒子在图里只能属于一个连通分量，
**不可能同时属于两个协作边界**。多边界在推导下**根本不存在**。

**理由二：「拓扑孤立」被推导判成「不属于这个协作边界」**

这两件事在业务上可以分开。一只在业务上属于 WMS、但**不跟边界内任何盒子交接**的盒子
（例如一只合规检查盒，产出一份合规报告，谁也不接、它也不接谁），
推导会把它踢出去——**它在图里是孤立分量**。

> **但理由二有个前提必须说清**：声明派若配一条守卫
> 「`boxes` 里的每只盒子在本边界至少有一条边」（§14），
> 就**把「拓扑孤立」也堵死了**——那条守卫等于宣布「**拓扑孤立 ≠ 协作边界成员**」，
> 跟推导的效果一样了。
>
> **所以真正的待定是那条守卫该怎么写**（§13 第 13 条）：
> - 守卫写成**硬禁止** → 单边界场景下，声明派与推导派**效果相同**，差异只剩多边界
> - 守卫写成**「孤岛必须显式点名」**（不许静默，但可以显式豁免）→
>   声明派能表达「业务上属于、拓扑上独立」的盒子，推导派不能
>
> **倾向后者**：硬禁止把「拓扑孤立」直接判成「不属于这个协作边界」——
> 而那正是本节要避免的事。**孤岛不是错，孤岛没被说出来才是错。**

**决定**：协作边界声明里必须明确写出有哪些盒子（`boxes` 字段保留），**不推导**。

**推论（多边界仍然可能）**：`boxes` 是声明的，所以一只盒子出现在 N 个协作边界的 `boxes` 里，
就属于这 N 个协作边界（§2.2 的能力**保住了**）。
代价是 §13 第 8 条（多边界下同一对盒子的边写几遍）**不能靠「多边界不存在」绕开**，
得正面回答。

**代价（诚实清单，补进 §9）**：
- 盒子清单要手工维护 → **已有守卫兜底**（D1 + D9 + 「孤岛须显式」，见 §14）
- 协作边界的边界可能与接线脱节 → **已被规则覆盖**（`all_archived` 会抓出「加进协作边界忘了归档」）

### 12.2 字段名：`members` → **`boxes`**（已定，2026-11-05）

**为什么改名**：`member` 一词在仓里**已经有第二个意思**——
`boxes/wms_design/domain.py` 的 `WMS_ENTITIES`（`sku` / `owner` / `warehouse` / `zone` /
`location` / `inventory` / `inbound` / `outbound` / `wave` / `lot` / `count`），
业务上它们也叫「WMS 这个协作边界的成员」。

**这是 §1.5 记的那类撞名的第二次发生**：上次是 `domain` 一词指两个东西
（分组标签 vs DDD 领域本体），这次是 `member` 一词会指两个东西
（**盒子** vs **领域实体**）。

**而且它会在升格那一刻变成真事故**：待定第 4 条若选「WMS 词表升格」，
`fulfillment_scopes/wms/` 里就会同时躺着

```
fulfillment_scopes/wms/
  ├─ domain.py     ← 协作边界的「成员」= 7 只盒子
  └─ entities.py   ← WMS 领协作边界的「成员」= 11 个概念实体
```

**同一个目录、同一个「成员」词、两个意思。**

**决定**：

| | 用什么词 | 是什么 |
|---|---|---|
| 协作边界声明的字段 | **`boxes`** | 本边界有哪些**盒子**（部署 / 接线单位）|
| WMS 领域本体 | **`entities`**（实体）| 这个领域有哪些**概念**（业务对象）|

**改名成本为零**：`member` / `members` 在整个代码仓里**零出现**，只存在于本文档。



### 12.3 关于 `core/scaffold.py` 改名（2026-11-05 讨论）

**问题**：「脚手架」这个词在仓里被两个东西占了——

| | 是什么 | 住哪 |
|---|---|---|
| **脚手架** | **生成代码**的工具 | `scripts/new_box.py` |
| **装配器** | 把声明装成产物，**装配期报错** | `core/scaffold.py` |

而 `architecture-upgrade.md` 的标题「盒子脚手架化」指的是**整个改造**
（把「复制模板」变成「按协议填组件」），不是某一个文件。

**三个选项**：

| | 命名 | 成本 | 判断 |
|---|---|---|---|
| A | `core/<box_scaffold>.py` + `core/<domain_scaffold>.py` | 40 文件 | 与 `architecture-upgrade.md` 用词一致；跟 `scripts/new_box.py` 仍撞 |
| B | `core/<box_assembler>.py` + `core/<domain_assembler>.py` | 40 文件 | ✅ **彻底分开**：脚手架=生成、装配器=装配 |
| C | 不改（`core/scaffold.py` + `core/<fulfillment_scope>.py`）| **0** | 靠类名区分（`assemble` vs `assemble_domain`），已经够 |

**倾向 B**：消掉的是贯穿全仓的术语歧义，而不只是文件名好看。
`assembler` 也更准——`assemble()` 干的事就是装配，而 `scaffold` 在编程里
通常指「项目脚手架/生成器」，正好是 `scripts/new_box.py` 的事。

**但 `core/models.py` 不跟着改**——它现在装的是**新旧两套盒子协议**
（`BeeBoxDefinition` + `PlacementDef` 即将退休）。等 12 只盒子迁完，
它瘦成「盒子和协作边界共用的公共类型」，**那时 `models.py` 这个名字恰好合适**。
现在改是替未来还债。

**执行时机**：**等 12 只盒子迁完再一次性改**。改名的 40 个文件里，
36 个是 `boxes/<盒>/{__init__,beeline,definition}.py`——正在被迁移改着，
现在动会撞车。

**参照**：`core/field_map.py` → `core/<wiring>.py` 只牵 5 个文件 + 1 个测试文件，
可以在同一批里顺手改掉。

    - 完整论证见 §12.1
    - **连带**：多边界仍然可能 → 第 8 条（边写几遍）**不能靠「多边界不存在」绕开**，得正面回答
13. **（新增，2026-11-05）孤立的盒子能不能算协作边界成员？**
    - 「一只盒子在 `boxes` 里，但在本边界一条边都没有」——**允许吗？**
      一只合规检查盒（产出一份合规报告，谁也不接、它也不接谁）业务上属于 WMS 协作边界，
      但它在图里是**孤立分量**。
    - 三个选项：
      - (a) **硬禁止**——`boxes` 里的每只盒子在本边界至少有一条边。
        单边界场景下声明派与推导派**效果相同**，「声明」只剩多边界这一个理由
      - (b) **孤岛必须显式点名**（倾向）——不许**静默**地孤岛，但可以在规则里显式豁免。
        「加进协作边界忘了接边」照样红（因为没点名），「它就是独立的」也能表达（显式点名）
      - (c) **完全不管**——孤岛就孤岛。**不行**：「加进协作边界忘了接边」会静默通过
    > **倾向 (b)**：孤岛不是错，**孤岛没被说出来才是错**。
14. ~~**豁免怎么表达「禁止」？**~~ → **2026-11-05 已定：`RuleExemption(box_id, reason, mode)`**
    - `mode="may"`（允许不做）/ `mode="must"`（**不得做**）
    - 「需求盒不得归档」是 **`must`**——写成 `may` **拦不住**有人给它补一条归档边
    - `reason` **结构化**（不放在注释里）→ 体检台能把它显示出来
    - D14（豁免的盒子存在、reason 非空）/ D15（`must` 不得有对应边）
15. ~~**跨边界关系是各协作边界独立关系，还是同一关系的多个视图？**~~ → **2026-11-05 已定：各协作边界独立关系**
    - **边只在「两端都在本边界」的边界里声明一次**
    - 跨边界的那一条，由**接收方协作边界**声明（`external=True`），源协作边界**不重复声明**
    - 一只盒子在 N 个协作边界的 `boxes` 里 → 它在每个协作边界的视角里都有位置；
      它与**同一协作边界**内盒子的边，在每个协作边界**各自声明**（接线上下文不同，是**不同的边**）
    - **绝不允许**：同一对盒子的同一条边在两个协作边界里各写一遍（那才是两份事实）
16. ~~**第一版是否需要历史协作边界版本？**~~ → **2026-11-05 已定：不做，但留钩子**
    - **现在没人需要**（附录 A4）
    - **事实层已经有了**：运行记录（`task_run` + `subject_ref` + `handoff`）证明实际发生了什么。
      协作边界版本化解决的是「回看当时的**接线**」——**回看接线 ≠ 回看事实**
    - **钩子两条**：① 协议里 `id` 已在，将来加 `version` **不改形状**；
      ② 记录履约时**把当时的协作边界 id 记进去**（一行），将来能按协作边界聚合
    - **不建完整发布系统**

## 14. 实现时必须同时补的守卫

**这份稿子实现完成前，它描述的一切都还不存在。** 实现时必须同时上：

- **D1–D12**（§5）——边界级装配期校验
- **D3c 的兼容判定不许自己写一套类型规则**——
  它必须和运行时的 `validate_payload` **共用同一份「什么类型算兼容」**（§5.6）。
  守卫也不许自己抄一份形状比较（那会是第二份事实）
- **「拿一份样例试一下」不算兼容判定**——
  它只能证明「**存在**一个合规产出能过」，不能证明「**所有**合规产出都能过」（§5.6 的 enum 反例）
- **「协作边界声明必须真的在装配」**——声明写在文件里没人装 = 没迁移
  （与 `architecture-upgrade.md` §5 的「新盒子必须真的在装配」同族）
- **「退休名不得回代码」**——`placement.domain` / `feeds_into` / `feedback_into`
  退休后，不得再被定义（判据：**不许再定义**，不是「字符串里不许有」——
  兼容层与别名表里出现旧名是故意的）
- **「盒子与边对得上」**——协作边界声明的 `boxes` 与 `edges` 的端点必须一致
- **「孤岛必须显式点名」**——`boxes` 里的每只盒子，在**本边界**至少有一条边；
  做不到的（**拓扑孤立**）必须在某条规则里**显式点名豁免**。
  抓的是「加进协作边界忘了接边」——
  这是 `boxes` 改成声明式之后**必须配套**的守卫。
  > **为什么不是「硬禁止孤岛」**：硬禁止等于宣布「拓扑孤立 ≠ 协作边界成员」，
  > 那就等于用拓扑替业务做判断（§12.1 的修正框）。
  > **孤岛不是错，孤岛没被说出来才是错。**
- **「盒子不留协作边界信息」**——新协议的 `BoxDeclaration` 里不许再出现
  `domain` / `feeds_into` / `feedback_into` 三个字段
- **「边界级规则不是自证的」**——规则里不许出现「盒子数 == N」这种数自己的读数；
  判据要引用**协作边界声明之外**的事实（注册表 / 盒子的 schema）
