### 0.2 空白在哪

概念上是**扁的**——只有「盒子」和「跳」两层，没有第三样东西安放**横切能力**
（权限、审计、限流、证据登记、证据投递）。

这些东西现在有两个去处，都不对：

- 塞进 `Component` 的字段 → 组件变成杂物袋
- 塞进 runtime 的硬编码 → 业务知识漏进内核

所以：**给 core 引入两个基本概念 —— 组件（component）与插件（plugin）。**

**分界线只有一条**：

> **主职责用组件实现；围绕主职责增加的能力用插件实现。**

## 1. 概念定义

### 1.1 组件（component）

> **组件 = 有明确输入、明确输出、明确边界的可组合单元。**

#### 1.1.1 统一契约

| 概念层叫什么 | 是什么 | 代码层 |
| --- | --- | --- |
| **作业组件**（最小组件） | 一跳。吃什么、吐什么、数据从哪来、下一步去哪、谁来实现 | `Component`（`core/scaffold.py`） |
| **复合组件** | 内部含子组件，且**自己声明** input / output | `BoxDeclaration` + `components`（今天盒子内部是一条线性链） |

**组件的契约只有一层**：**接口契约**——有 `input`、有 `output`（都是 schema id）。
组件**不承诺判据**：判据是**履约契约**，在履约单元级（§3.2 说清为什么）。

**「契约」这个词有三层，别混用**：

| 契约 | 答什么 | 在哪 |
| --- | --- | --- |
| **接口契约** | 这一块吃什么、吐什么 | 组件级：`input` / `output`（都是 schema id） |
| **履约契约** | 这次履约交付什么、怎么算对 | 履约单元级：`result_schema` + `acceptance` + `exceptions` |
| **插件契约** | 插件挂在哪、作用在哪、实现从哪来 | 插件级：`PluginSpec` + `PluginType` + `PluginBinding`（§4.2） |

#### 1.1.2 组合：递归是目标模型，**本期只落地两层**

**目标模型**是递归组合：

```text
BeeBox
└── 复合组件 A
    ├── 作业组件 B
    └── 复合组件 C
        └── 作业组件 D
```

一个普通复合组件被另一个组件引用、装配、执行；插件可以挂在**任意节点**上
（包括中间的复合组件 A）。

**但本期只支持两层**（盒子 → 作业组件）：

| 层 | 本期状态 |
| --- | --- |
| 盒子 → 作业组件 | ✅ 已支持（盒子内部是一条线性链） |
| 复合组件 → 复合组件 | ❌ **未支持**，是下一阶段（§7 的 M6） |
| 插件挂在中间复合组件上 | ❌ 随上一条一起 |

**为什么要写清楚**：仓库里现在**确实只有两层**。
说成「组件可以包含组件已经是事实」是夸大——
**事实是「盒子包含作业组件」**，不是「组件可以包含组件」。
一般复合组件要能被别人引用、装配、执行，需要**共同协议 + 递归装配规则**
（§3.1 给了规则草案），那是下一阶段的事。

#### 1.1.3 命名

**为什么给「一跳」起个专门的名字**：概念层的「组件」是**任何**可组合单元，
它包含作业组件和复合组件。若代码里的 `Component` 也被叫「组件」，
一个词就背了两套语义——读者按名字猜，猜错就按错的东西找。
所以概念层正式叫「**作业组件**」；代码标识符 `Component` **暂不改**（§1.5 说清代价与改的时机）。

### 1.2 盒子（beeBox）= 履约单元

> **盒子是复合组件的一种角色**：复合组件 **+ 产出契约 + 判据 + 例外 + 政策 + 度量**。

盒子自己的形状：

| 复合组件的位置 | 盒子里对应什么 |
| --- | --- |
| input | `task_schema`（投料入口的形状） |
| output | `result_schema`（产出契约的形状） |
| 子组件 | `components` 里的每一跳 |

**盒子额外要满足履约约束**：接什么任务、交付什么结果、怎么验收、怎么留下证据。
所以——

> **不是任意复合组件都能叫 BeeBox。只有通过履约装配校验的组件，才叫 BeeBox。**

这已经是现状：装配器在盒子被注册、被投料之前，就把自相矛盾的声明拒了
（`AssemblyError`）。**「BeeBox」不是一种声明形态，是一道通过的结果。**

**判据是「履约契约」，不是「验收组件」。** beeOS 的判据是 runtime 的**契约闸**
（`runtime/contract.py` 的结构校验 + `runtime/acceptance.py` 的业务验收）：
它读最终产出、判对错、**不产出物、不进链、不进产出契约**。
若把判据做成链上一跳，就得回答「判定结果进不进产出」——那是另一个量级的改动，
不属于本次。**判据留在履约契约层（§3.2）。**

### 1.3 插件（plugin）

> **插件 = 挂在组件上的横切扩展。它不能独立存在。**

#### 1.3.1 插件 = 宿主约束 + 扩展点契约 + 实现绑定

一个插件类型要能真的跑起来，必须说清三件事：

| 要说清的 | 答什么 | 落在 |
| --- | --- | --- |
| **宿主约束** | 允许挂在哪类宿主上（作业级 / 盒级 / 都行） | `PluginType.allowed_hosts` |
| **扩展点契约** | 作用在哪个钩子上；钩子递给它什么；允许它返回什么 | `PluginType.extension_points` + §4.6 的调用契约 |
| **实现绑定** | 实现从哪来；装配期怎么确认它**真的存在** | `PluginType.implementation_key` + 装配期查表 |

**三件缺一件，插件就只是一个名字**：
只有宿主没有实现 = 挂上去也不会被调用；
只有实现没有扩展点 = 不知道什么时候该调它。

#### 1.3.2 扩展点（extension point）

扩展点是**具名钩子**：runtime 在哪些位置留了口子，插件就挂上去。

| 钩子（示意） | 时机 | 典型用途 |
| --- | --- | --- |
| 执行前 | 这一跳执行**之前** | 权限校验、投料准入 |
| 执行外层 | **包裹**这一跳的执行 | 重试策略、超时 |
| 执行后 | 这一跳**之后** | 审计、证据登记、通知 |
| 升级决策 | 验收失败且例外要求升级时 | queen 决策 |

**扩展点不是封闭枚举**——它是 runtime 留的钩子，**由 runtime 注册它有哪些**。
core 只定义「插件要声明它作用在哪个钩子上」这个协议，
**不认具体钩子的名字**（否则 core 就得反向依赖 runtime）。

**queen 用的不是通用「执行后」**：它的触发条件是
「验收失败 **且** 例外写了 `escalate`」，返回的是**一个完整的决策对象**，
runtime 拿它改状态机。所以它需要**自己的钩子**，
不是一个可以到处挂的 `after`（§7 的 M3）。

#### 1.3.3 五条纪律

1. **必有宿主** —— **结构上保证**，不是靠校验：
   插件只可能出现在 `Component.plugins`（挂某一跳）或 `BoxDeclaration.plugins`（挂整盒）
   两个列表里，**没有第三种放法** → 插件不可能悬空。
   *「算了却看不见」「声明了却拿不到」那族病的入口，就是悬空。*
2. **不承载形状** —— 插件不改宿主的 `input` / `output`。
   改形状是组件自己的事（那不是横切，是改内容）。
   模型层就不给插件留形状字段 → 这条在**声明层**是结构保证。
3. **不许触碰宿主内部** —— 这条**不是结构保证**，是**机制保证**：
   runtime 只递给插件**受限视图**（明确字段 + 深拷贝），
   插件拿到的本来就是副本，改不到宿主的数据（§4.6）。
   *为什么强调这一条*：不给声明模型加字段，只能限制**声明方式**，
   挡不住 Python 实现修改传入对象。**边界要靠调用接口 + 运行时检查来撑。*
4. **宿主可以声明「我必需某类插件」** —— **这是宿主级的要求，不放在插件类型上**。
   同一个插件类型，A 盒必须装、B 盒不必装——
   这在类型上一个布尔值表达不了。所以声明在宿主上：
   `requires_plugins: list[str]`（插件类型 id）。
   缺了就**装配期报错**，不等到运行时才发现。
5. **不登记没人能执行的插件类型** —— 类型表里只放**当场能被强制**的类型。
   *前例就在仓里：`idempotency.mode=required` 全仓没人声明，
   因为跨履约的去重台账还没做 —— 声明一个没人兑现的承诺，比不声明更坏。*

### 1.4 「插件」这个词的撞名

`docs/architecture-upgrade.md` 第 2 节第 1 条决策里那处「插件」指的是**盒子**
（与继承式相对的那套组装方式）。全仓文档里这个词只出现那一次。

→ 那处改成「**协议式组装**」，把「插件」整个留给新概念。
（M0 做，并加进退休词名单：文档层与代码层都不许再出现旧义。）

### 1.5 「Component」这个标识符：现在不改，以及改的时机

代码里的 `Component` 专指**作业组件**（一跳），而概念层的「组件」是任何可组合单元。
一个词背两套语义，得处理。处理方式有三条：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A（本次采用）** | 概念层正式叫「作业组件」；代码标识符不动 | 无。读者按文档读、按代码读，各准 |
| B | 改名 `Component` → 作业组件类名 | 机械改动散布在每一跳 × 全部盒子 + 脚手架模板 + 守卫 |
| C | 现在就引入通用组件类（`Component` = 通用），作业组件改成它的具体类型 | 同 B，另加一次协议设计 |

**为什么本次选 A**：方案 B/C 有一个**隐藏的连锁**——

仓里的退休机制是「旧名不许再**定义**」，判据落在 AST 的类名上。
把 `Component` 改名并退休，等于**烧掉 `Component` 这个标识符**；
而通用组件概念将来若要落成代码里的类，名字本来就该叫 `Component`——
**烧了就回不来**。

所以：**通用组件概念今天只活在文档层，不落成类。**
`Component`（作业组件）与 `BoxDeclaration`（复合组件）两个具体类型，
已经把「组件」的两种形态都覆盖了。

**什么时候改**：等通用组件真的要成为代码里的类时，**一次性做完**——
改名 + 退休旧名 + 引入通用类，三件事落在**同一批**里，
不留「旧名还在、通用类又来了」的两套事实。

> 这个决定不是「以后再说」——它带着**明确的触发条件**：
> **通用组件成为代码里的类的那一批**。

## 2. 层次与不变式

```text
        插件（宿主约束 + 扩展点契约 + 实现绑定）
                    │  挂载（只有两个位置）
                    ▼
        组件（接口契约：input / output，可嵌套）
                    │
     ┌──────────────┴──────────────┐
     ▼                             ▼
作业组件（一跳）              复合组件（盒子）
`Component`                  `BoxDeclaration` + `components`
                                 │
                                 └─ 子组件：若干作业组件
```

**不变式（core 装配期必须验）**

| # | 不变式 | 落在哪 |
| --- | --- | --- |
| I1 | 组件的 input / output 都必须是本盒声明过的 schema id | ✅ 已有 |
| I2 | 复合组件的每一跳都必须可达（无孤岛） | ✅ 已有 |
| I3 | 组件链恰好一个入口，且入口吃的就是投料 | ✅ 已有 |
| I4 | **插件必有宿主** | ✅ **结构保证**（只有两个列表可放） |
| I5 | **插件类型已登记**（不登记的类型不许用） | 🆕 新校验 |
| I6 | **该类型允许挂在这种宿主上** | 🆕 新校验 |
| I7 | **扩展点已注册**（runtime 留了这个钩子） | 🆕 新校验 |
| I8 | **绑定参数合法**（符合该类型的参数模型） | 🆕 新校验 |
| I9 | **同一宿主同一插件类型只挂一次** | 🆕 新校验 |
| I10 | **决策类钩子每个宿主只允许一个绑定** | 🆕 新校验 |
| I11 | **实现存在**（实现键非空 + 在实现表里 + 可调用） | 🆕 新校验 |
| I12 | **宿主声明的必需插件都已挂上**（`requires_plugins`） | 🆕 新校验 |
| I13 | **插件类型在全仓只登记一次**（重复登记当场报错） | 🆕 新校验 |
| I14 | **该扩展点在这类宿主上会触发**（挂上去 ≠ 会被调用） | 🆕 新校验 |
| I15 | **插件不改形状** | ✅ **结构保证**（声明层没有形状字段） |
| I16 | **插件不触碰宿主内部** | ⚠️ **机制保证**（受限深拷贝视图），**不是**结构保证 |
| I17 | **插件改不到自己的配置**（参数逐次深拷贝） | 机制保证（runtime 的调用点） |
| I18 | **返回值完整且合法**（决策类：四項齐 + 词在词表里） | 机制保证（runtime 的调用点） |
| I19 | **插件失败 → 履约中止，不降级**；落哪个状态**按失败发生在哪一段**（§4.6.7） | 机制保证（runtime 的调用点） |

**I14 为什么单独一条**：「能挂上去」不等于「会被调用」——
扩展点只在它声明的宿主上触发。挂到不触发它的宿主上，
装配通过、运行时**永远不会被调用**，
而读者以为它在守着——这就是「声明了却没人执行」，装配期本该拦住的。

## 3. 三件必须先定死的语义

### 3.1 嵌套的边界语义：子组件的产出怎么并进父组件

**先说现状**：数据是**直通传递**的——下一跳吃的是上一跳的**整个产出**
（`runtime/executor.py` 里 `op_input = dict(op_output)`）。
**仓库里没有「统一上下文」这个东西**，别写「子组件的产出进的是上下文」——
那是下一阶段递归组合才需要的机制，届时必须显式定义
（谁建、装什么、子组件怎么读）。

规则（**在现状的线性直通下退化成立**，所以不破坏任何现有盒子）：

- 复合组件的 **input** 必须让**第一个子组件**吃得下（形状相容）
- **父组件对外承诺的必填字段，必须由内部执行结果保证提供**。
  线性直通下 ⇒ **末个子组件的输出 ⊇ 父组件的输出必填字段**（方向：**父 ⊆ 子**）
- 父组件若要**转换 / 筛选 / 汇总**子组件的结果，
  **必须显式声明输出映射**。没有映射就没有来源 ⇒ 装配期报红

**为什么方向必须是「父 ⊆ 子」**：父承诺的必填字段若不在子组件的输出里，
那个字段**没有来源**——它既不是子组件算出来的，也不是映射给的，
就是凭空承诺。反过来（父多给子）只在「父要转换」时才成立，
而那种情况必须由**输出映射**显式承担。

> 现状的 C10 比这条还严：它直接判**末跳的 `output` 与 `result_schema` 是同一个 schema id**。
> 本期不变——上面这条是给**递归组合阶段**用的规则，
> 今天的线性链上它退化成 C10。

### 3.2 判据在哪一级：**履约单元级（盒子），不在组件级**

判据答的是「这次履约的**业务结果**对不对」——那是**结果级**的问题。
若每跳都写判据：

- 跳数 × 判据数 爆炸
- 「末跳产出 == 产出契约」这条失效——产出契约是**盒子级**的
- 且判据读的字段必须在**最终产出**里，不是每一跳的中间产出里

所以：

| 层级 | 带什么 |
| --- | --- |
| 组件（作业 / 复合） | 接口契约：`input` / `output` / `next` / 插件 |
| 履约单元（盒子） | 额外带：`result_schema` + `acceptance` + `exceptions` + `queen` + `metrics` |

### 3.3 组件属性 vs 插件：**`idempotency` / `leaves_artifact` 不迁**

| | **组件属性** | **插件** |
| --- | --- | --- |
| 是什么 | 这一跳**自己**的执行属性 | 围着主职责**加**的能力 |
| 例子 | 能不能重放、会不会留东西 | 权限、审计、限流、证据登记 |
| 谁读 | runtime 的重试判据与状态判定 | 扩展点上的调用 |
| 要加新东西时 | 改组件模型 | 挂一个插件 |

`idempotency` / `leaves_artifact` 属于**左边**：
它们跟这一跳的执行方式绑在一起（runtime 的重试判据直接读 `op.idempotency.mode`），
不是「围着主职责加的」。

**所以它们留在组件字段上，不迁成插件。**

**迁走的代价**：每一跳 × 全部盒子 + 夹具盒 + 直接构造 `Operation` 的十几处测试
+ 三份文档，**换来的是「概念统一」，不是新能力**。
这件事的收益撑不起那个代价。

**推论**：插件**只有一种形态**——介入型（带扩展点 + 实现绑定）。
不存在「声明型插件」这种形态，因为仓里那两条声明型的事实
（幂等、留产物）都留在了组件字段上。
**不造没人用的形态。**

## 4. 代码层怎么落

### 4.1 命名与撞名处理

| 概念层 | 代码层 | 处理 |
| --- | --- | --- |
| 组件（作业） | `Component`（现有，= 一跳） | **暂不改名**。文档写清两级含义；概念升格 ≠ 改名 |
| 复合组件 / 履约单元 | `BoxDeclaration` + `components` | 现状即如此 |
| 插件类型 | 🆕 `PluginType`（登记在**开放的**类型表里） | 类型可由 core / runtime / boxes 贡献 |
| 插件声明 | 🆕 `PluginSpec`（宿主上写的） | |
| 插件绑定 | 🆕 `PluginBinding`（装配产物） | 见 §4.5 |

**为什么插件不需要「作用对象」字段**：宿主由**所在位置**决定
（`Component.plugins` = 这一跳，`BoxDeclaration.plugins` = 整盒）。
带 `target` 就多一份可能指空的事实，多一种写法，多一条要守的规则。

### 4.2 新增模型（core，纯协议，不含业务）

```python
# core 的插件协议模块（M1 新建，模块路径 `core.plugins`）

#: 宿主种类
HostKind = Literal["op", "box"]


class PluginSpec(BaseModel):
    """宿主上写的一个插件声明"""
    model_config = ConfigDict(extra="forbid")

    id: str = Field(description="插件类型 id")
    extension_point: str = Field(description="作用在哪个钩子上")
    params: dict[str, Any] = Field(
        default_factory=dict, description="插件参数（形状由类型定）"
    )


class PluginBinding(BaseModel):
    """装配产物：已校验、已定位实现的插件绑定（**可序列化**）"""
    model_config = ConfigDict(extra="forbid")

    id: str = Field(description="插件类型 id")
    extension_point: str = Field(description="作用在哪个钩子上")
    params: dict[str, Any] = Field(default_factory=dict)
    implementation_key: str = Field(description="实现在哪张表里")


@dataclass(frozen=True)
class PluginType:
    """一种插件类型：宿主约束 + 扩展点契约 + 实现绑定"""
    id: str                                  # 插件类型 id
    allowed_hosts: tuple[HostKind, ...]      # 允许挂在哪类宿主上
    extension_points: tuple[str, ...]        # 允许的作用位置（钩子 id）
    implementation_key: str = ""             # 实现在哪张表里
    params_model: Optional[type[BaseModel]] = None   # None = 该类型不带参数
    summary: str = ""
```

**「声明」与「绑定」的区别**：`PluginSpec` 是宿主上写的（人写的），
`PluginBinding` 是装配器校验完编出来的（机器产的）。
**绑定只带实现键，不带实现**——因为 `Operation` 必须可序列化（§4.5）。

**扩展点的隶属关系**：`PluginSpec.extension_point` 必须在
该类型的 `PluginType.extension_points` 集合里（不在 → 装配期报红）。

**为什么 `PluginType` 上没有「必需」这一维**：
「必须装权限插件」是**某个宿主的要求**，不是类型的要求——
A 盒必须装、B 盒不必装，同一个类型表达不了这个差异。
所以它住在宿主上：`requires_plugins: list[str]`。

### 4.3 插件类型表：**开放注册**

core 定义**协议 + 注册机制 + 校验规则**，**不认具体业务**。

| 谁 | 贡献什么 |
| --- | --- |
| `core/` | 插件协议、注册机制、**校验规则**（登记的形状怎么判、宿主约束怎么判、扩展点怎么判、实现怎么查） |
| `runtime/` | **通用**插件实现 + **它留了哪些扩展点钩子**（钩子注册表） |
| `boxes/*` | **业务**插件类型 + 它的参数模型 + 它的实现 |

**为什么类型表必须开放**：core 若独占类型表，
新增一种业务插件就得**改内核**——业务扩展又回到「改内核」，
而内核的改动要动全部盒子。
「core 提供机制，boxes 定义业务组件和业务插件」这句话要求的
就是**注册表向业务侧开放**。

**注册必须受控**：受控的是**登记的形状与校验**，不是**业务内容**。
core 校验每一次登记：参数模型给了吗、宿主约束写了吗、
扩展点在钩子注册表里吗、实现绑定的键在实现表里吗。
**业务内容由业务侧贡献。**

**重复登记同一个类型 id 怎么办**：当场报错。
同一个 id 登记两次 = 两个来源说同一件事，迟早给出不同答案（§2 的 I13）。

#### 登记主体：谁登记、谁使用

| 插件类型 | 登记主体 | 使用方 |
| --- | --- | --- |
| **通用**（queen、通用审计…） | **公共提供方**（runtime / core）登记**一次** | 只声明绑定 |
| **业务**（某盒子的证据登记…） | **所属业务模块**登记**一次** | 只声明绑定 |

**使用方永远只声明绑定，不登记类型。**
登记是**归属方**的事——这跟 handler 表的逻辑一样：
实现属于提供方，使用方只是引用。

「登记一次」+「使用方只声明」这两条合起来，才能同时做到：
**共享**（多个盒子用同一个类型）、**显式**（谁提供的一目了然）、
**不靠 import 顺序碰运气**（公共提供方必然先于使用方 import，
因为盒子依赖 core / runtime）。

**装配时冻结**：装配器把**类型表**与**实现表**复制一份快照，放进 `AssembledBox`。
运行时用的是这份**快照**，不是那张还在别处被改动的活表。
理由跟「runtime 不查全局注册表」同源：**装配期是唯一的解析点**，
运行时要看到的必须跟装配时看到的一致。

**core 与 runtime 都不 import 具体盒子**：盒子在 import 时登记自己的类型，
装配入口负责把登记收齐（§4.4）。

### 4.4 注册与装配：两段式启动的事实约束

**一个必须先解决的事实**：现在每只盒子在 **import 时就装配**
（`boxes/*/__init__.py` 里 `ASSEMBLED = assemble(...)` 写死在模块顶层）。
所以「先把所有插件类型登记齐，再统一装配」这件事**今天做不到**——
盒子 A 引用盒子 B 登记的类型时，B 可能还没被 import。

两条路：

| | 做法 | 代价 |
| --- | --- | --- |
| **自包含**（本期） | 通用类型由**公共提供方**登记一次，业务类型由**所属模块**登记一次，**使用方只声明绑定** | 简单，零启动改动。代价：**跨盒共享的业务类型**要等两段式启动 |
| **两段式启动**（下一阶段） | 先 import 全部盒子（登记），再统一装配 | 要改装配时机，是独立的一批 |

**顺序依赖的边界（要写准）**：

- **通用类型**：公共提供方（runtime / core）必然先于任何盒子 import
  （盒子依赖 core / runtime）→ **顺序天然确定**，本期就能用。
- **跨盒共享的业务类型**：登记方是某个业务模块，而另一个盒子可能先被 import
  → **本期不支持**，要等两段式启动。
- **同盒自包含**：盒子自己登记自己用的业务类型 → 顺序确定，本期就能用。

**中间必须有的诚实**：装配期遇到未登记的插件类型时，
报错要说清三件事——「这个 id 没登记」+「现在注册表里有哪些」+
「**是不是导入顺序问题**」。否则读者会去查类型表，而真因是导入顺序。

### 4.5 从声明到运行时的传递路径

**这一段必须写死**，否则「插件声明了但运行时拿不到」就会发生：

```text
宿主的插件声明（Component.plugins / BoxDeclaration.plugins）
  → 装配器校验（I5–I14：类型 / 宿主 / 扩展点 / 参数 / 重复 / 实现键 / 扩展点触发范围）
  → 编译成插件绑定 PluginBinding（类型 + **规范化后的参数** + 扩展点 + 实现键）
  → 进 Operation.plugins（跳级）/ BeeBoxDefinition.plugins（盒级）
  → 类型表与实现表的**快照**进 AssembledBox（装配时冻结）
  → Runtime 按宿主 + 扩展点，从**快照**里取实现来调
```

**绑定里的参数是「规范化后的」那一份**（补了默认值、转换了类型），不是声明原文：
参数模型允许省略（有默认值），也允许字符串转数字（`"4"` → `4`）。
直接用原文的话，插件拿到的就少了默认值、或者拿到没转换的字符串——
**声明说是一回事，传给插件是另一回事**。

**必须选定一种，不留第二种**：

- **绑定放 `Operation` / `BeeBoxDefinition`**（本次选定）——
  **不放**独立的执行计划，也**不**另开一张全局表。
- **Runtime 只用装配结果**（那份**冻结的快照**），**不重新查全局注册表**。

**为什么实现不进 `Operation`**：`Operation` 必须**可序列化**
（作业路线要落盘、要导出 JSON 做差分比对）。
所以绑定里放**实现键**，实现本体跟 handler 一样走**盒子给的表**——
`HandlerRunner` 已经解决过同一个问题，照抄它的形状就行。

**为什么 runtime 不查全局注册表**：运行时再查一次 = 装配期校验形同虚设
（装配时存在的实现，运行时不保证在），而且那是**第二份事实**。
**装配期是唯一的解析点。**

### 4.6 运行时调用契约

#### 4.6.1 调用粒度：一次「调用」里含多次「尝试」

```text
一次组件调用（call）         ← 插件边界在这一层
└── 多次执行尝试（attempt）   ← 重试在这一层
```

**现在的代码不是这样**：重试循环和 op 调用是同一层
（`runtime/executor.py` 的 `while` 循环体就是一次尝试）。
要支持 per_call 的**op 级**插件，**执行器要把这两层拆开**。

**这一拆分属于 M5，不属于 M2**：

- **M2 只实现升级决策钩子所需的调用机制**——
  升级决策是**盒级**钩子，在 beeline 走完之后调一次，
  **不需要**先重构 op 的重试循环。
- **执行器的「调用 / 尝试」拆分、`around`、逐次语义**一起进 **M5**。

（这一条曾经同时写在 M2 和 M5 两处，是本稿的内部矛盾，已统一为 M5。）

**每个钩子声明它的粒度**：

| 粒度 | 一次宿主调用里被调几次 | 典型 |
| --- | --- | --- |
| `per_call`（默认） | 一次 | 升级决策、审计收尾 |
| `per_attempt` | 每次尝试一次 | 限流、逐次审计 |

#### 4.6.2 绑定顺序

按**宿主声明的列表顺序**（`plugins` 列表的顺序），
**不按注册顺序**——注册顺序取决于 import 顺序，不能让它影响业务行为。

#### 4.6.3 插件能碰到什么

runtime 只递给它**受限视图**——扩展点明确列出的字段 + **深拷贝**；
**参数也逐次深拷贝**。

**为什么参数也要拷贝**：视图是副本，参数也必须是——
否则插件改了自己的配置，改的是**原始声明**，
下一次履约拿到的配置就变了，而且看不出是谁改的。
（这条是 2026-11-13 的 CR 修出来的：原来参数是直接传的。）

**这条保证的边界（必须写准）**：它保证的是
**「插件无法通过传入视图直接修改宿主数据，也无法改掉自己的配置」**。
**它不保证**：同进程 Python 插件的闭包、全局引用、外部副作用
（写文件、发请求、起进程）——深拷贝管不到那些。
要管住它们要的是**进程隔离**，那是能力层的事（§10）。

#### 4.6.4 插件能返回什么

由**扩展点的返回契约**定，每个钩子自己声明：

| 钩子类型 | 返回 |
| --- | --- |
| 决策类 | 一个**完整的决策对象**（不是光一个词）——见 §4.6.5 |
| 动作类（执行前 / 执行后） | `None`，或一份**受限补丁** |

**返回值不合契约 = 插件失败**（→ §4.6.7 的中止路径），
不是「凑合着用」。理由跟别的契约一样：
放行一个不合契约的返回值，等于让 runtime 按一个它没验过的东西改状态。

#### 4.6.5 决策类钩子：返回完整对象

一次决策**不只是一个词**。现在的 `QueenDecision` 带四项：

```text
decision / reason / triggered_rule / unusable_rules
```

四项**一起**进 `policy_decision`。所以钩子必须返回**完整对象**，runtime 三件事都要做：

- **校验决策词在词表里**（`runtime/models.py` 是唯一真源）
  ——不认识的词 = 契约错误 = 中止，**不猜**
- **校验四項都在**——少一项读者就看不到发生了什么
- **保存**整份决策（含理由与用不上的规则），再**应用**状态转换

**只返回一个字符串，就等于把理由和证据扔了**——
那正是「用不上的规则必须看得见」这条纪律要防的事。

**「有 decision 键」不算通过**：一个不认识的词放行，
履约会按错的词落状态，而没人知道插件说了一句 runtime 不懂的话。

#### 4.6.6 补丁能改什么

补丁不是万能后门，**能改什么必须写死**：

| | 允许 |
| --- | --- |
| **能追加** | 证据、元数据、审计条目（**只增不改**的字段） |
| **不能改** | 业务结果字段、判据读数、任务状态、投料内容 |

**必须重新校验**：补丁合并后的产出**重新过一遍 schema 校验**——
补丁碰过的字段不许绕开契约闸。

#### 4.6.7 插件失败了怎么办

- **不降级**：宿主履约中止。
- **状态怎么落，要看插件失败发生在哪一段**——状态机是白名单，不能乱转：

| 失败发生在 | 当前状态 | 落哪个状态 | 为什么 |
| --- | --- | --- | --- |
| 组件执行**途中**（op 级插件） | `running` | 有残留 → `partially_completed`；无残留 → `failed` | 现有口径：链没走完 + 有东西留在现场 → 部分完成 |
| **升级决策**（盒级，queen 那类） | `completed` | **`failed`** | `completed → partially_completed` **不被状态机允许**；`completed → failed` 允许。且语义对：这次没交付，**且没人接**（该接的人没被通知到）——与「验收判红且没匹配到例外」同一口径 |

**升级决策插件异常必须落盘**：失败原因进事件流 + 状态 reason，
不能只在内存里抛一下。

**「已留产物 → partially_completed」这条规则的适用范围**（要写准）：

- 它现在只覆盖**链没走完**的路径（`_end_unfinished` 那条）。
- **链走完之后的残留判定，现状就不做**——
  验收判红时落 `failed` / `rejected` / `waiting_external`，**不看有没有残留**。
- 所以「链走完 + 插件失败 + 前面留了东西」这个组合，
  现有状态机**表达不了**（`completed → partially_completed` 不允许）。

**这是已知缺口，不是本次引入的**：验收判红的路径今天就有同样的问题
（开发盒提交了代码、验收判红 → 落 `failed`，读者从状态看不出现场有残留）。

**本次不扩展它**——那要加状态机转换 + 改状态表 + 改看板，
是「验收层残留判定」的独立改造（§11 记一笔）。
插件失败**沿用验收同一口径**，不顺手改语义。

> 另外一条要说准的：`leaves_artifact=True` 是**「这一跳可能产生副作用」的声明**，
> **不代表副作用真的发生了**。runtime 现有判法是「已完成的跳里有没有声明了留产物的」
> ——判的是**声明**，不是**事实**。
> 声明会撒谎（盒子声明了但没留，或留了但没声明）。
> 要判事实得靠**真实副作用追踪**，那是能力层的事（§10），不在本方案范围。

## 5. core / runtime / boxes 三层分工

| 层 | 装什么 | 不装什么 |
| --- | --- | --- |
| `core/` | 组件协议 / 插件协议 / 注册机制 / 校验规则 / 装配器 | **任何业务**（现状如此） |
| `runtime/` | 执行作业组件、在扩展点上调用插件、管理状态、记录证据；**通用插件实现**（重试、审计这类）+ **扩展点钩子注册表** | 业务知识（`runtime/queen.py` 的纪律：runtime 不许出现业务词，有守卫盯着） |
| `boxes/` | 业务组件（每盒的组件链 + schemas + handlers）、**业务插件类型与实现**、业务插件的取值 | 机制、校验 |

**通用实现为什么放 runtime 而不是 core**：core 是**协议**（只定「能声明什么」），
runtime 是**执行**（真的把它做出来）。通用重试、审计这类能力不带业务知识，
放 runtime 既不违反「core 不含业务」，也不违反「runtime 不许有业务词」。

## 6. 不做的事（写进文档，防后来人走偏）

1. **不引入继承式组件基类。**
   复用靠**组合**（引用 + 覆写），不靠继承。
   继承式 = 样板从文件搬进类（且更隐蔽，方法体里的样板 diff 看不见），
   还会让「声明与实现的接缝」变成隐式 —— 继承来的 handler 与继承来的声明
   会**错位**，而这种错位**装配期查不出来**（装配器查的是「type 在不在
   handler 表里」，不查「handler 的行为符不符合声明」）。
2. **不引入 DSL。** 业务组件仍用 Python 写 handler。
3. **不造第二个「插件」词。** 盒子不叫插件（见 §1.4）。
4. **不把判据下沉到组件级。** 判据是结果级的（§3.2）。
5. **不让插件承载形状。** 改形状是组件自己的事。
6. **不造「声明型插件」这种形态。** 仓里那两条声明型的事实
   （幂等、留产物）留在组件字段上（§3.3）——**不造没人用的形态**。
7. **不把「不改形状 / 不碰内部」说成结构保证。**
   前者在**声明层**成立，后者要靠**调用接口 + 运行时检查**（§1.3.3 第 3 条、§4.6）。
8. **不给插件加「作用对象」字段。** 宿主由所在位置决定（§4.1）。
9. **不把「必需插件」放在插件类型上。** 它是**宿主的要求**（§1.3.3 第 4 条）。
10. **不登记没人能执行的插件类型。**（§1.3.3 第 5 条）
11. **不把判据做成组件。** 判据是履约契约的一部分，是 runtime 的契约闸——
    不产出物、不进链、不进产出契约（§1.2）。
12. **不改 `Component` 的标识符。** 改名会**烧掉**这个标识符
    （退休机制：旧名不许再定义），而通用组件概念将来要用的正是它——
    等通用组件真要落成代码里的类的那一批，一次性改（§1.5）。
13. **不在本期做递归组合。** 本期两层（§1.1.2），递归是下一阶段。
14. **不把插件实现塞进 `Operation`。** `Operation` 必须可序列化
    （落盘 + 导出 JSON 做差分）；实现跟 handler 一样走盒子给的表（§4.5）。
15. **不把「插件不能改宿主数据」说成绝对保证。**
    深拷贝只挡住「通过传入视图直接改」（§4.6.3）。

### 7.1 收编 queen：范围比想象的小

查证结果：**`QueenDef` 里 runtime 真正消费的只有 `rules.exception_handling.escalation_rules` 一处**
（`runtime/queen.py` 里 `queen_rules.get("exception_handling")` → `escalation_rules`）。

其余配置**当前没有 runtime 消费点**：

| 配置 | 有没有 runtime 消费点 |
| --- | --- |
| `authorization.task_routing` | ❌ 无 |
| `authorization.exception_handling` | ❌ 无 |
| `authorization.continuous_improvement` | ❌ 无 |
| `rules.task_routing` | ❌ 无 |
| `rules.continuous_improvement` | ❌ 无（只有盒子的指标计算在用，不是 runtime） |

**这意味着两件事**：

1. **M3 不能整体退休 `BoxDeclaration.queen`**——它还装着那几档配置。
   M3 只迁**唯一被消费的那一块**，`QueenRules.exception_handling` 这一格退休，
   `queen` 字段本身保留。
2. **那几档「无消费点」的配置是「声明了却没人执行」**——
   这是**现状**，不是插件化引入的。本次**不动**它们，
   但要在盒子的声明里**如实标注**（读者不该以为它们在起作用）。
   要让它们生效、或者让它们退休，是**独立的一件事**，不属于本方案（§11）。

### 7.2 为什么第一个插件是 **queen**

盒级插件不用新造——仓里已经有一个几乎完整的原型：**queen**。

| queen 现状 | 在哪 |
| --- | --- |
| 挂在盒子上 | `BoxDeclaration.queen`（`core/scaffold.py`） |
| 盒子声明规则，runtime 做**通用求值** | `runtime/queen.py`（runtime 里不许出现业务词，有守卫盯着） |
| 触发条件明确 | 验收失败 **且** 例外写 `escalate`（`runtime/acceptance.py`） |
| 返回值明确 | **完整决策对象**（四项）；**没有决策函数时默认交给人**（`runtime/models.py` 是词表唯一真源） |
| 决策**记进 task run**（`policy_decision`），可追溯 | |
| 行为已验证 | 已上线，已跑过真实履约 |

**它缺的只是「叫它插件」**——形态已经是盒级插件了：
盒级宿主 + 声明驱动 + 公共层实现 + 记录证据。

所以 M3 选它，理由有三：

1. **不用新造能力**。审计 / 限流 / 权限这些**都还不存在**，
   造一个出来就是「声明了却没人执行」；queen 是**已经能执行**的那一个。
2. **它是这套机制的第一个真插件**。宿主约束、扩展点契约、实现绑定三件事
   同时被一个真实用例验过，而不是纸上谈兵。
3. **收编它是行为等价的**。声明层换个挂载方式，runtime 的求值逻辑不动。

**它不是「通用执行后」**：queen 的钩子只在「验收失败且要升级」时触发，
返回的是完整决策对象而不是补丁。这条在 M2 的钩子契约里写死（§4.6.5）。

### 7.3 第一个**业务**插件（M4 的候选）

机制要证明的是「**boxes 自主贡献**」，所以还得有一个**业务侧登记**的类型。
仓里现成的候选：

| 候选 | 为什么天然是业务插件 | 代价 |
| --- | --- | --- |
| **证据登记** | 每只盒子的证据**形状不同**（WMS 盒子的 7 项 evidence、学习盒的记录），抽取规则是业务的 | 改行为（证据登记的时机与形状） |
| **度量采集** | 每盒的度量算法本来就是业务代码，现在登记在 `kanban/trigger.py` 的 `METRIC_COMPUTERS` 里 | 改行为；且要动看板取数 |

**两者都要改行为，所以 M4 单独拍板**（§11）。选哪个，取决于哪个先有真实需求。

| 「不改形状」被当成结构保证 | 文档里分开说：形状是**声明层**结构保证；内部访问是**机制保证**（§1.3.3 第 3 条） |

| **重试与插件调用次数打架** | 执行器拆成「一次调用 → 多次尝试」两层（**M5**）；钩子声明粒度（per_call / per_attempt）（§4.6.1） |
| **绑定顺序受 import 顺序影响** | 按**宿主声明的列表顺序**执行，不按注册顺序（§4.6.2） |
| **决策只返回一个词，证据丢了** | 决策类钩子返回**完整决策对象**，runtime 校验词表、保存四项、再应用状态转换（§4.6.5） |

| **「链走完后的残留」表达不了** | 已知缺口（验收判红路径今天同样有），本次**不扩展**；要改得加状态机转换 + 改状态表，单独一批（§11） |
| **共享插件的登记主体不清** | 通用型由公共提供方登记一次，业务型由所属模块登记一次，**使用方只声明绑定**；装配时**冻结**类型表与实现表（§4.3） |
| **跨盒共享的业务类型被 import 顺序卡住** | 本期明确不支持，要等两段式启动；报错说清「是不是导入顺序问题」（§4.4） |
| 补丁变成万能后门 | 补丁只能**追加**证据与元数据；改业务结果/判据读数/状态一律不许；合并后重新过 schema 校验（§4.6.6） |
| 登记顺序让装配报假错 | 报错写清「没登记 + 已登记有哪些 + 是不是导入顺序」；两段式启动列为下一阶段（§4.4） |
| 嵌套语义把线性链搞复杂 | §3.1 的规则在现状下退化成立 → M0–M2 零行为变化 |
| 递归组合被当成已经支持 | §1.1.2 明确写成**阶段限制**：本期只有两层 |
| 「组件」一词两义（通用组件 / 作业组件） | 概念层正式叫「作业组件」；代码 `Component` 暂不改（§1.5 写清了改的时机与代价） |
| 改 `Component` 会烧掉标识符 | 本次不改；改名与引入通用类必须落在**同一批**，不留两套事实（§1.5） |
| 改到一半发现判据层级选错 | M1–M3 全部**不改变运行时行为**，判据层级要改也是后面的批次，且会单独拍板 |
| 运行时层那条手写路径（夹具盒）忘了迁 | 涉及 `Operation` 字段的批次要把它列进同一批；否则它就是第二套事实的起点 |

## 9. 验收形态

### 9.1 声明结构：允许变，但归一规则提前写死

增加 `plugins` 字段、迁移 `queen` 的一格，**必然改变序列化结果**。
所以「声明 JSON 逐字节不变」这个说法在 M1 之后**不成立**。

**改成两条**：

| 什么 | 要求 |
| --- | --- |
| 声明**结构** | **允许变**，但归一规则**提前写死**（差分脚本里列明哪几个字段归一掉） |
| **运行行为** | **必须不变**：状态机终态、产出 payload、决策理由与证据 |

**归一只许归一「这次刻意加的字段」**——
不许拿宽泛的归一把别的变化一起盖掉。
归一是「把新加的插件字段去掉再比」，不是「把差异都抹平」。

**归一规则有两类，都要写进差分脚本**：

| 类型 | 出现在 | 规则 |
| --- | --- | --- |
| **新增字段** | M1 / M2 | 去掉新加的 `plugins` 字段再比 |
| **字段搬迁** | M3 | 规则从 `queen.rules.exception_handling.escalation_rules` 搬到了插件参数里 → **先断言两处逐条相同**，再把两处**归一到同一个结构**再比 |

**字段搬迁的顺序不能反**：先断言（搬迁没改内容），再归一（去掉位置差异）。
反过来做，就等于把「内容变了」也一起盖掉。

**必须逐项相同的关键项**（差分脚本逐项断言，不是整体哈希）：

- 终态（`task_run.status`）
- 每跳的产出 payload
- `policy_decision` 的四项（`decision` / `reason` / `triggered_rule` / `unusable_rules`）
- 事件流（事件序列与条数）

### 9.2 其他验收

- 全部已注册盒子仍装得出来（装配器现有校验 + 新增校验各自验）
- 每一跳的声明 JSON 与作业路线 JSON **归一后**逐字节不变
- 真跑链路逐字节相同（每只盒子各跑一次）
- 装出来的包自带测试跑得绿（若走打包）

## 10. 与「编程语言级」那条线的关系

这套模型是**能力系统（effect / capability）的协议层**：

- 插件 = 横切能力的载体
- 插件类型 = 「这个组件允许做什么、作用在哪、实现从哪来」的声明处
- 扩展点 = **强制**的落点：插件只能在这几个钩子上被调用，
  别的位置它够不着

真正的**强制**（运行时拦住越权：agent 只能发它声明过的请求、只能写它声明过的路径）
属于运行时的能力层，是**下一阶段**的事——本设计先把「能声明什么」这件事
钉成协议，装配期就能验。

一句话：**协议先行，强制后至。**
所以「不登记没人能执行的插件类型」这条纪律（§1.3.3 第 5 条）是这条线的**地基**：
先有兑现得了的协议，再谈更强的强制。

**深拷贝不是隔离**：同进程 Python 插件的闭包、全局引用与外部副作用
不受深拷贝约束。要真的管住它们，要的是**进程隔离**——
那是能力层的事，属于「强制后至」那一阶段。

## 11. 还剩五件待拍板

1. **M4 选哪个业务插件？** 候选：**证据登记** / **度量采集** / 其他。
   两者都改行为，所以单独拍板。选哪个取决于哪个先有真实需求。
2. **两段式启动做不做？** 自包含（本期）还是两段式（下一阶段）。
   本稿建议**先自包含**，把两段式放到 M6 一起做——
   因为递归组合本来就要改装配时机。
3. **递归组合（M6）排不排进这一轮？** 本稿建议**不排**：
   它要重写装配器（递归装配 + 复合组件的输出映射），是独立的一个量级。
   排期之前，先把 M0–M3 走完——那三批证明的是「机制 + 第一个真插件」。
4. **queen 那几档「无消费点」的配置怎么处理？**（§7.1）
   本稿建议**本期只如实标注**（读者不该以为它们在起作用），
   要让它们生效或让它们退休，**另开一批**——
   那件事跟插件化无关，是「声明了却没人执行」的清理。
5. **「链走完之后的现场残留」要不要补？**（§4.6.7）
   现状：`running → partially_completed` 允许，**`completed → partially_completed` 不允许**；
   所以「验收判红 / 插件失败 + 前面留了东西」这个组合，
   履约层只能说 `failed`，读者从状态**看不出现场有残留**。
   本稿建议**本期不补**（那要加状态机转换 + 改状态表 + 改看板），
   但要**记下来**——它是「状态说谎」的同一族病，
   跟插件化无关，是验收层的独立改造。

### 12.4 一轮 CR 修掉的五个洞（2026-11-13）

上一版 M3 落地后，外部评审复现了五个洞。**五条全部属实**，
逐条对代码核实后都修了：

| # | 洞 | 修法 |
| --- | --- | --- |
| P1-1 | op 插件能装到盒级钩子上，**永远不会被调用** | 扩展点新增 `host_kinds`；装配期拒「这个钩子不在这类宿主上触发」的绑定（I14） |
| P1-2 | 非法决策词 / 缺字段的决策**被当成正常业务决定** | 扩展点新增 `return_required_fields` + `decision_values`；不合契约 = 契约失败 = 履约中止（I18） |
| P2-3 | 空实现键绕过「实现存在」检查（空串是假值） | 空键 / 没登记 / 不可调用，一律装配期拒 |
| P2-4 | 参数验证结果被丢弃，绑定里还是原文 | 绑定存**规范化后**的参数（补默认值、转换类型） |
| P2-5 | 插件改自己的参数 → 改的是**原始声明** | 参数**逐次深拷贝**后再递给插件（I17） |

**共同的病根**：上一版把「能挂上去」当成了「会被调用」，
把「声明合法」当成了「运行时会照着做」。
**装配期该拦的，不能留到运行时**——
更不能留到「永远不发生」（那比报错更坏）。
