# BeeBox Workshop

做 BeeBox 的工作台。第一版只做一件事：**体检台**——把一只盒子声明得对不对，
摊开给人看。只读。

## 怎么打开

跟看板同一个服务、同一个端口：

- 页面：`/workshop`
- 整个目录的体检结论：`GET /api/boxes/health`
- 单只盒子的体检结论：`GET /api/boxes/{id}/health`

## 它和看板的区别

| | 看板 | 工作台 |
|---|---|---|
| 看什么 | 故障 | 盒子本身 |
| 回答 | 「现在哪儿坏了」 | 「这只盒子声明得对不对」 |
| 能不能改 | 不能 | 现在也不能 |

看板那边不放能改东西的入口——看板是盯故障的面，
在它上面放「改声明」的按钮，等于让修机器的人顺手改了机器。

**目录平级，进程不分开**：`workshop/` 和 `kanban/` 平级，跑在同一个服务上。
什么时候值得拆进程？三条判据同时成立才拆：权限不同、发布节奏不同、
负载特征不同。现在一条都不成立。

## 判定住在哪

```
boxes/<id>/definition.py     声明（事实与承诺）
        │
        ▼
kanban/catalog.py            攒出体检材料（知道注册表的那一层）
        │
        ▼
runtime/box_health.py        判定（内核，不 import 盒子）
        │
        ├──► tests/test_box_standard.py   守卫：红的就红
        └──► workshop/views.py            页面：把同一份结论摊开
```

**一处判定，两处引用**。守卫和页面读的是同一份结论，所以它们**必然**一致——
不是靠两边小心保持一致，是它们读的是同一份判定。

以前「盒子合不合规」只住在 pytest 断言里。工作台要给人看同一批结论，
照抄一遍就会出现两套口径：守卫说绿、页面说红，而且没人知道该信哪个。

## 三态

每条检查有三种结果，页面上长得不一样：

| 状态 | 意思 |
|---|---|
| 已验 · 通过 | 验过了，成立 |
| 已验 · 有问题 | 验过了，不成立 |
| 没验到 | **材料没给，或者这件事现在算不出来** |

「没验到」**不算通过**——那是在给一件没验过的事发合格证。
所以材料缺了的时候，页面上是「没验到」，不是绿。

## 验什么

每条检查都带着「为什么重要」——不写这一栏，看的就只是红绿两色，
不知道红在哪、值不值得修。

- 引用的形状都存在（判据、例外、作业路线指着声明过的形状吗）
- 判据读得到值（读不到 = 恒过或恒红，两种都是坏结果）
- 例外条件读得到值（读不到 = 规则永远不触发，**安静地没做**）
- 例外条件真的能触发（它要求一个该字段装不下的值吗）
- 条件里的值类型对得上字段类型
- 示例投料投得出去（用户复制粘贴就能用）
- 成熟度跟自己的声明对得上（零判据会被判成「全过」——那是谎）
- 归属字段填了
- 声明的指标有人算
- 有执行器

## 现在没有什么

- **不能改声明**——第一版只读
- **没有发布/版本实体**——`release_id` 现在是拼出来的字符串，没有打包、
  校验和、历史。发布和分发都要等地基
- **没有市场**——BeeBox Market（成熟 BeeBox 的目录）还没做。
  它的 Certification 卡片里，静态那半张就是这套检查；
  履约事实那半张要等履约历史接进来
- **不装第三方盒子**——没有沙箱、没有依赖管理、没有凭证隔离、没有签名。
  在这四样东西齐了之前，「安装别人的代码」是把自己交给别人
